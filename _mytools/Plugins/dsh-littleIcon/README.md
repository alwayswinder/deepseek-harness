# @local/dsh-little-icon

English | [中文](README.zh.md)

## Summary

The pet is a **process of its own** (PowerShell + WPF), not an overlay inside the DSH window: it owns a frameless, transparent, always-on-top window, so it stays on the desktop while the DSH window is minimized or tucked away. The host half (`index.js`) samples agent state into a state file; the pet switches its animation from it. Clicking the pet calls user32 `ShowWindow` to tuck the DSH window away or bring it back, and its right-click menu offers the same action plus a position reset and quit. Its first four menu entries belong to the page: **Chat** opens chat.deepseek.com in DSH's embedded browser, **Git changes** opens a repository page in the right Sidebar — the current Session's uncommitted changes on the left, its commit history on the right — the last ten first, reading on as the list is scrolled, and narrowable to one author — plus an explicit fast-forward pull — **Open working directory** hands that same directory to the file manager, and **Settings** puts the **Plugins** page on this bundle's own card, where the pet's controls live; **mini games** hangs a submenu whose **glass aquarium** entry opens another plugin's fullscreen WebGL overlay. **Music** hangs a submenu of its own, rebuilt from the library the host publishes at every open: a grey line saying what is playing, paused, or waiting, **Play**/**Pause** with **Next song** and **Previous song**, **Download missing songs (N)** while files are missing, **Open the music folder**, and **Settings**; the pet's own process plays the audio, so the music keeps going after DSH is tucked away. **Screenshot** is the pet's own move rather than the page's: a region dragged on a dimmed sheet over the whole desktop lands as a PNG under `$DSH_HOME/little-icon/shots/`, with the picture itself left on the clipboard. The plugin adds no model-visible input of its own; **Commit and push** remains an ordinary user message sent only when clicked.

## Use this package

**Desktop install.** Desktop owns its own configuration (`$DSH_HOME/profiles/desktop`) and refuses `dsh plugin --profile desktop`; fill this directory's absolute path into the application's **Plugins → Add plugin** dialog once per machine. Desktop must then be restarted: the host half (`index.js`) takes no part in client hot reload, so only a restart loads it.

**Web install** (optional; there the pet only floats and controls no window). `build/start-dsh.bat` already lists this plugin in `DSH_LOCAL_PLUGINS`, so every start idempotently installs this directory into the web profile as a `file:` copy, and `sync-plugins.bat` refreshes `index.js`, `pet/`, and `assets/` with it. To install it by hand:

```text
dsh plugin --profile web add file:<repo>/_mytools/Plugins/dsh-littleIcon
```

**Size and translucency.** Open the **Plugins** list and click the **Desktop Pet** card: the settings card is drawn on that card's page, between the description and the parts list, so nothing hides behind the `little-icon` row. It leads with:

- **Sites** — one line per site: its **note** on the left (the name the menu shows; leave it empty to use the address's host) and its **address** on the right (a missing `https://` is completed for you). **Remove** drops a row and **Add a site** appends one. The right-click menu's Sites submenu lists them in this order, and a row whose address is not HTTP/HTTPS (`file://`, say) or carries a user name says so under its own boxes instead of quietly missing from the menu;
- **Volume** — a 0–100 slider (`musicVolume`, 70 by default) for what the pet plays at; it travels in the settings file, so both machines share it;
- **Music folder** — the folder the audio files are downloaded into (`musicDir`), with a **Browse** button beside it; empty keeps the plugin's own `$DSH_HOME/little-icon/music/`;
- **Music** — the listening part: the link list, the **Download missing (N)** button, and the **Now playing** line with play, pause, previous, and next (see "Listening to music" below);
- **Size** — a 96–320 pixel slider; the pet takes the new size within a frame;
- **Translucent while idle** — a switch; turn it off and the pet never fades;
- **Translucency** — available while that switch is on, 15%–100%;
- **Tuck DSH away behind another app** — on by default, with its **tuck away after going behind** slider (0 seconds) greyed out while the switch is off;
- plus enable, always-on-top, click behaviour, and animation pace, with idle pacing, the happy duration, and the state sampling interval folded under **More**.

Controls write straight to the profile configuration (the `little-icon` entry in `$DSH_HOME/profiles/<profile>/cordis.patch.yml`) and need no restart: the host republishes the state file on a config change and the pet applies it within a second. Toggling **Enable the pet** off and on also ends and restarts the pet process at once. A second and a half after an edit the host also **copies that entry into the repository's [../../settings/pet-settings.yml](../../settings/pet-settings.yml)** — only the desktop profile saves on its own, while committing and pushing stay yours to do — and the same route carries the **Desktop's shortcuts**: that document belongs to the main process (`$DSH_HOME\desktop\electron-user-data\keybindings.json`), whose edits this half never sees, so it watches the file itself and copies it into [../../settings/keybindings.json](../../settings/keybindings.json) as soon as the app rewrites it. `build\start-desktop.bat` (or a restart from the pet's menu) merges both files back into whichever machine starts next, so two computers never configure the pet or the shortcuts twice. A value edited on this machine in the meantime survives until its file changes again; `node _mytools\settings\sync-settings.mjs apply --force` pulls the files' values back over it (the mechanism is in the working copy's `_mytools/README.md`, under the settings section). The card comes from the plugin's own browser half (`client.js`), so no second, automatically generated form appears after a restart.

**Interaction.** The pet starts in the bottom-right corner of the primary screen, as translucent as configured, and fully visible under the pointer. Dragging with the left button moves it (the position is stored on release, restored on the next start, and clamped onto the current virtual screen). A **click** — a press that did not move the window — performs the configured `clickAction`: `toggle` (default) tucks DSH away only while it is the window in front; a DSH that is merely behind another application is brought forward instead, and one that is away is restored and foregrounded. `minimize` only minimizes, `none` does nothing. Its right-click menu offers Chat, Sites, Git changes, open working directory, mini games, music, screenshot, special features, and settings, plus a Desktop-only **System** submenu holding update, restart, and quit. Besides your own clicks, the pet tucks DSH away on its own once DSH goes behind — see "Tucking DSH away behind another app" below.

**Right-click menu.** Right-clicking the pet opens the plugin's only menu — the pet no longer has a tray icon of its own, because DSH's main process already keeps one and an accessory should not add a second. The menu is a white rounded card with fine-outline icons, a soft shadow, a restrained hover fill, and a divider before the **System** submenu; native placement keeps it inside the working area, while an outside click or Escape dismisses it. Its first four entries belong to the page, then the pet takes its own screenshot, a **Special** submenu hangs the capabilities that start something of their own, and **Settings** closes the group above the divider. It carries no window utilities: clicking the pet is the tuck route (DSH's own tray icon is the other), and the pet's position only ever moves by dragging it. **Chat** brings DSH back on screen and to the front first — tucked away, minimized, or merely behind another window — and only then opens <https://chat.deepseek.com>. **Where it opens follows "Open chat links in" in Settings → General**, the same preference DSH applies to a chat link in a conversation: **In-App Sidebar** puts it in DSH's own **right-Sidebar Browser tab**, while **Default Browser** hands it to the system browser. **Sites** is the second: a submenu that opens nothing itself, listing the sites configured in the settings (see **Sites** under "Size and translucency" above and the `sites` field below) — the note is the entry's name, and hovering one shows its address. Choosing any of them brings DSH back on screen the way Chat does and then opens that address at **the same destination**; with an empty list the submenu says so and its last entry, **Manage sites**, is the **Settings** command that turns the Plugins page to this bundle's card. The list travels in the state file and the submenu is rebuilt at every open, so an edit in the card needs no restart on either side. Only HTTP/HTTPS addresses are offered (a missing scheme is completed with `https://`); a `file:` or `javascript:` address, or one carrying a user name and password, is kept out of the menu by the Host. **Sign-ins** are kept by that Browser tab per **workspace** while the preference sends these entries there: after signing in there once, neither a restart nor a rebuild asks again (see "Known limitations"). Choosing **Default Browser** puts the sign-in in that browser's own profile instead. **Git changes** restores the window the same way and then opens the plugin's own **Git page** (below) in the right Sidebar: the current Session's working directory, with its **uncommitted changes** (including new, untracked files) on the left and its **commit history** on the right — the last ten first, reading on as the list is scrolled, and narrowable to one author; double-clicking a row on either side opens what is behind it — that file's diff, or that commit's files. Restoring the window first is not optional: a tab opened in a window nobody can see is a tab nobody sees. **Open working directory** is the fourth: it hands the current Session's directory to the Host, which starts `explorer.exe` on it — the page knows which directory but has no process, the Host has a process but no notion of a current Session, so each half contributes what it has (see "Opening the working directory" below). Unlike the other two it does **not** bring DSH back on screen first: the folder window is what the person asked to see, and Explorer raises itself. **Settings** is last, and the only entry about the plugin rather than about the Session: it restores the window the way Chat does, then asks the **Plugins** page to open this bundle's card — the same card the Plugins list shows, with the size, opacity, sleep, screenshot folder, and click controls on it. That page belongs to the plugin manager, so this is cross-plugin navigation through the service the page provides (`ctx.pluginNavigation.openBundle`) rather than a route of this plugin's own; the pet only names the entry and the page does the rest. **Mini games** is another submenu: it opens nothing itself, so more games can join without changing the menu's shape. Its first child is **glass aquarium**, which the page owns like the entries above and therefore raises DSH for the same reason — a fullscreen overlay in a hidden window is an overlay nobody sees. The page opens it through the service that other plugin provides (`ctx.get('aquarium3d')`), so the pet only names the game; without that plugin installed the entry logs a warning instead of opening a blank screen. **Music** is the third submenu, and the one the pet performs itself: it sits between **mini games** and **screenshot**, its entries are rebuilt from the library the Host publishes at every open, and its commands never leave the pet's process, which is why the song keeps playing after DSH is tucked away. It leads with a grey status line — **Now playing: <title>**, **Paused: <title>**, **Ready: <title>** before anything has started, **Playback failed: <reason>** when the file could not be played, **No songs downloaded yet** with nothing downloaded at all, or **<N> not downloaded yet** when nothing is downloaded but links are waiting — then **Play**/**Pause** (whichever the state calls for), **Next song**, and **Previous song**; while a fill-in is running that group collapses into one grey line, **Downloading: <done>/<total>**; then **Download missing songs (<N>)** while files are missing, or the grey **Every song is downloaded** when none are; then **Open the music folder**, which the Host hands to Explorer; and last **Settings**, the same command the main menu's own **Settings** is — it restores DSH first and then turns the Plugins page to this bundle's card. **Special** sits between the screenshot and **Settings** and, like **mini games**, opens nothing itself: a capability that starts something of its own lives one level down, so a second one can join without reshaping the menu. Its first entry is **Multi-machine**, a submenu the pet rebuilds from the Host's state at every open — a grey status line reading **Not running**, **Host - waiting for the other computer**, **Host - connected** (with the peer's round-trip time once it has one, and **remote mode** appended while the host is in it), **Client - connected**, or **Client - reconnecting**; then a grey line for the host address and a grey line for the switch hotkey; then a divider; then **Start and connect** or **Stop**, whichever the running state calls for; and last **Settings**, which opens this bundle's card. Below the divider, the **System** submenu opens nothing itself and holds three entries: **Update DSH** builds the current checkout and restarts only after success (below), followed by **restart DSH** (which asks first, then ends DSH and starts it again exactly as it was — below) and last **quit DSH**, which asks for confirmation first (quitting interrupts whatever is running) and then **ends the Electron main process of DSH**. That entry used to post `WM_CLOSE` to the DSH main window — the same route as its own title-bar close button — but the desktop now makes closing a window **hide it to the tray** (the X button only tucks DSH away), so that route no longer ends anything. Ending the main process makes the Host child notice the closed channel and run its own shutdown (sessions flushed, agents stopped); that shutdown unloads the plugin, whose cleanup ends the pet with it, and a timer's host-liveness check is the fallback. The pet process draws the menu and the page performs what it chooses, with the Host carrying the choice between them; where the page has no Browser tab to open (a Web profile leaves it disabled), **Chat** and **Sites** fall back to the system browser — the same fallback `ui-chat` takes for a conversation link — with a warning saying why, instead of failing — **Git changes** needs no shipped tab type, so any build with a right Sidebar can open it. **The pet never quits itself from the menu**: its lifetime belongs to the **Enable the pet** switch, and a menu entry that ended it would bypass that switch.

**The Git page.** **Git changes** opens one page in the right Sidebar, split into two scrolling columns; a Sidebar too narrow for both stacks them into two rows of equal height, each keeping its own scrollport:

- **Uncommitted changes** on the left: everything `git status --porcelain` reports — staged, unstaged, and **untracked new files** (with `-uall`, so files inside a new directory are listed one by one rather than collapsed into the directory name). Each row carries the status word (new, modified, deleted, renamed, copied, conflicted, type changed), the path, and, for the entries already in the index, a "staged" marker;
- **Recent commits** on the right: the repository's commit history, each on three lines — the **message** (wrapped, so a long subject is never cut off), the **short hash**, and the author with the local time. It opens on the last `10`, reads the next `10` as the list is scrolled to its end (the row at the end of the list reads the same page on a click), and stops at the repository's first commit; a read in flight, a failed read, and a repository that cannot be read each say so on that row, which turns into **Retry** when a page failed.
- **Filter by author**, under the heading on the right: the select lists every author this history has, with how many commits each wrote (two identities sharing a name are told apart by their full address on hover). Choosing one leaves that author's commits alone in the column, read `10` at a time the same way; **All authors** puts the whole history back. A filter the repository the page just moved to does not have falls back to **All authors** by itself.

**Double-clicking any row** hands both columns over to whatever that row is about, always under a **Back** button that returns to the listing:

- **A row on the left** (an uncommitted file) opens **that one file's diff**: its status word and full path sit in the header, and the text below is `+` green, `-` red, `@@` blue, file headers and `index` lines grey — keeping its own line breaks and scrolling sideways instead of wrapping. A diff past 200,000 characters is sent cut short, with a line of its own saying so. A tracked file is compared on whichever side of the index holds the change — both sides when both do, one block above the other — and an untracked new file is compared against an empty one, so a file that was just added still has a diff to show; `HEAD` is never the other side of the comparison, which is why a repository with no first commit yet works too.
- **A row on the right** (a commit) opens **the files that commit touched**: its message, the file count, and the short hash sit in the header, and each file is a row below — the status word (new, modified, deleted, renamed, copied, type changed) and the path, with a rename showing where it came from as "← old path" on the same row, because a move is one thing rather than a deletion plus an addition. A merge commit is compared against its **first parent**, so what it brought in is what you see instead of an empty list, and a commit that changed nothing says so in a line.

While a detail is open, **Refresh** re-reads that detail rather than dropping you back on the listing, and changing the Session or the working directory returns to it. A row highlights under the pointer, and its tooltip says what double-clicking it does.

A header line above them shows the repository root, the current branch, **Refresh**, **Pull**, and **Commit and push**. Beside **Recent commits**, a status pill contacts the configured upstream and says **Up to date**, how many commits are waiting to pull, whether the histories diverged, or why freshness cannot be determined. Opening the page and **Refresh** both update that check; it fetches only the branch's remote-tracking ref and does not move the local branch, index, or working tree. **Pull** runs `git pull --ff-only`, then replaces the listing with the refreshed repository state. It refuses a detached HEAD or a branch without an upstream, and authentication, timeout, or diverged-history failures leave the existing listing in place with an explanation. Nothing here stages, commits, pushes, reverts, or creates merge commits. The repository is whichever one the **current Session's working directory** is in, not a configured path — so the page follows the project the conversation is in, and a Session started in a subdirectory still shows the whole repository. A working directory outside every repository, a directory that is gone, and a machine with no `git` each get their own line and disable the action buttons; an empty repository (no first commit yet) is a normal state, with both columns saying they are empty.

**The Commit and push button.** It performs no Git operation itself; it **speaks for you**: it sends "审查本地改动，没有问题就提交并推送吧" into the current conversation as a **real user message**, through the same Host admission the composer uses (`ctx.conversation.send`, a queued turn). The button itself keeps the short "Commit and push" label while `COMMIT_AND_PUSH_PROMPT` holds the sentence it sends. The message therefore appears in the conversation, enters the session log, and reaches the model; it joins the queue when a turn is already running and starts one immediately when nothing is. The agent reviews the local changes first and commits and pushes only when it finds no problem, using its ordinary tools and the repository's commit-message convention. The button reports "Sent" (or "Queued" while a turn is running) where it stands, and shows the reason underneath when the message could not be sent — no live input channel for this Session, or the Host refusing the admission. **There is no confirmation step**: one click is your asking for the review and conditional commit and push.

**Opening the working directory.** The menu's **open working directory** entry hands the current Session's directory to the Host, which starts `explorer.exe` on that folder — the same window you get by pasting a path into the address bar. It is the directory the Git page reads too (the page takes the `cwd` of the Session the main view holds, the same source DSH's own "open workspace" header control uses); what differs is who performs the last step, because the page has no process and the Host has no notion of a current Session, so the page names the directory on `POST /api/little-icon/open?cwd=…` and the Host opens it. Unlike the Chat and Git entries this one does **not** bring DSH back on screen: the folder is what the person asked to see, and Explorer raises itself.

When it fails, the **pet** is what speaks: the Host publishes the last attempt that opened no folder into the state file (`notice: { at, reason }`, with `reason` one of `no-cwd`, `no-dir`, or `failed`), and the pet shows a message for a notice newer than the one it has already shown — the directory is gone, the Session has no working directory yet, or the folder could not be opened. That round trip exists because the **click happens on the pet**: a failure the Host merely logged is a failure nobody reads, and a menu entry that opens nothing reads as a broken entry. The timestamp keeps one failure to one message, and because the notice never changes once written it costs no extra writes. Nothing beyond the directory is validated — whether it is a Git repository does not matter; if it can be opened, it opens.

**Screenshot.** The menu's **screenshot** entry is the one action that never involves DSH at all: the region is dragged on the desktop rather than inside a window, so the pet dims every screen, draws the selection itself, and takes the PNG. That sheet is the pet's own topmost window over the whole **virtual screen** — a selection may therefore span monitors — and its window region has the selection cut out, so the hole is a **live** view of exactly what the file will hold rather than a schematic one, with a frame around it and the pixel count above it. Releasing the left button captures that rectangle into `shot-<timestamp>.png` (milliseconds in the name, so two captures in one second stay apart) inside the folder the **Screenshot folder** setting names — the plugin's own `$DSH_HOME/little-icon/shots/` while that setting is empty, which is what it starts as — and leaves the **picture itself** on the clipboard; a click that never dragged, a right-click, and Escape each back out without writing a file or saying anything. The image is the clipboard's only format: a target that takes an image — another chat window, a document, or DSH's own composer, whose paste intake turns it into a draft attachment — receives the picture, while a target that takes only text receives nothing rather than a path it would have to go and open. Where the file landed is what the notice above the pet says instead, and the picture is copied through the clipboard rather than referenced, so it stays pasteable after the pet exits. Where it landed is then said once, above the pet, for a few seconds; a capture that could not be saved is reported in the same message box an unopened folder gets. The sheet is a **WinForms** window rather than the pet's own WPF one because WinForms keeps every coordinate in physical pixels, the units `Screen` and `CopyFromScreen` use: WPF's device-independent units would drift from the shutter at any display scale other than 100%, which is the trap the pet's own window position avoids by staying in WPF's units. The capture is what the selection showed, the pet included when the region covers it.

**Listening to music.** The audio is played by the **pet's own process** through a WPF `MediaPlayer` over a local file, not by an `<audio>` element in the page — and because that window stays on the desktop while DSH is tucked away, the music does too. What the Host downloads is Bilibili's `30280` stream (about 192 kbps AAC in an `.m4a` container), written as it arrives with no transcoding. **Links are configuration, files are not**: `musicLinks` holds the addresses and the same mechanism as every other setting copies it into the repository's [../../settings/pet-settings.yml](../../settings/pet-settings.yml), so the repository carries links and **no audio**; the files land in `musicDir` (`$DSH_HOME/little-icon/music/` by default, with `~` and relative paths resolved against the user directory) and `$DSH_HOME/little-icon/music-index.json` records which file belongs to which id. A folder pointed inside the checkout is not used at all: the setting is ignored in favour of the default folder, the card says why, and the published library carries `inside-checkout`. The card's **Music** row is the working end: one line per link — the title with **downloaded** and a remove button once the file is there, the link itself with **not downloaded** (**download failed** after a failed attempt) and a remove button while it is not — a paste box with **Add** that writes `musicLinks` and downloads at once (a link already in the list answers "That link is already in the list.", and the Host deduplicates by video id so two addresses for one video do not both land), **Download missing (N)**, `N playable`, and a separate group for files on this machine that no link claims — usually a file whose link was removed — removable there. Below it, **Now playing: <title>** with play, pause, previous, and next buttons writes a command into `music.json` and lets the pet perform it. Removing the file that is playing is refused with "The pet is playing that file; switch song and remove it again.", and **changing the music folder does not move what is already downloaded** — the new folder has to be filled in again. **A second machine fills itself in with one click**: after `git pull` the links arrive with `pet-settings.yml` but no files do, so the menu shows **Download missing songs (N)** and the card shows **Download missing (N)**; one click downloads every missing link in order, pausing 400 ms between them, reports each failure (`video`, `audio`, `network`, `unrecognized`, `no-audio`, `write`) without interrupting the rest, and a second click retries only what is still missing; when it finishes the pet says **Done: N added, M failed** above itself. **A restart resumes**: the pet reads the song and the position back out of `music-player.json` and plays on if it was playing, and the page's commands carry timestamps, so a restart never replays one. The pet's own **Music** submenu carries the library's two other controls: a **Volume (N%)** submenu whose first row is a track bar with the number beside it — moving it is audible at once, and the value is written to the configuration once the drag settles, so one drag is one settings write — over the 0/25/50/75/100 presets, which move that same slider. **That volume is configuration, so the page performs it**, exactly as the card does: the settings service refuses any write made inside an HMR transaction, and the Host's timer runs in the context of the load that created it, so the command travels on the same stream as every other menu entry that changes something. **Adding and removing links stays on the card**, where a text field and a list belong, so the list has one owner. **One link is one set.** A link that names a part (`?p=N`) is that part; a bare video link stands for everything that video holds — every part of a multi-part video, or the episodes of the collection it belongs to — so one pasted address adds a hundred songs in one step. Adding is not fetching: a set is written into `musicLinks`, and **Download missing (N)** is what starts those files, because a hundred downloads are a decision rather than a side effect of a paste. **Long lists stay readable**: the parts of one video are folded into the set they came from — one line naming the video, `N songs · M here`, a toggle that shows them, and one button that drops the whole set (and this machine's files for it) instead of a hundred clicks; a single song is left as the one line it always was. Both write through the settings service the card writes through, so they land in the same profile row and the same checked-in settings file, and a menu click says what it did above the pet.

**Multi-machine.** Under **Special**, **Multi-machine** gives two machines one keyboard and mouse: the Host runs the plugin's own `bin/MouseShare.exe` — compiled from `_mytools/MouseShare/` by that tool's `build.bat`, which copies it here — as this machine's host or client, and that child process ends with DSH, leaving no listening port or global input hook behind. **Which side a machine takes is not configured**: the two machines share one setting, the machine with a network adapter on the address's IP becomes the host and listens on the address's port, and the other becomes the client and dials in. The connection therefore runs **from the client to the host** and retries every 3 seconds, so either machine may choose the entry first, and two machines on different subnets or behind NAT still connect. The settings sit on the card under **Screenshot folder**: **Host address** (`192.168.1.3:15180` by default), the only field to edit when the host's IP moves, **Switch hotkey** (`ctrl+alt+f12` by default), and **Start with DSH** (on by default, bringing the link up at that address as DSH starts with no menu entry to choose — while a link **stopped from the menu** is not restarted by any other settings write and waits for the next DSH start, the same rule **Enable the pet** follows). The hotkey is a manual fallback for a **pointer that normally crosses by itself**: the other machine sits to the left of this one, so reaching this screen's **left edge** hands the pointer over (the remote pointer enters at its own right edge, so it reads as one continuous movement) and pushing past the remote's **right edge** hands it back at this screen's left edge. The screen's top and bottom strips and any held mouse button are excluded, so the Start menu, a corner sweep, or a window dragged onto the edge never switches machine. While it is remote, this machine's own pointer stays where it was because the host has taken its events.

**Configuration fields.** These are the Host schema fields. The card writes the pet controls; `gitPullTimeoutMs` is profile-only. Every field applies live, so nothing needs a restart:

| Field | Default | Meaning |
| --- | --- | --- |
| `enabled` | `true` | Turning it off ends the pet process; turning it back on starts one |
| `size` | `160` | Window edge in pixels; the frames are built at 256px and scaled down |
| `translucent` | `true` | Whether the pet fades while the pointer is away |
| `idleOpacity` | `0.45` | How far it fades; hover is always 1. Ignored while `translucent` is off |
| `frameMs` | `600` | Milliseconds each animation frame stays on screen |
| `pollMs` | `800` | Host sampling interval; lower follows the agent sooner, higher costs less |
| `happyMs` | `3000` | How long a finished task keeps it happy before it idles again |
| `boredEverySeconds` | `60` | While the agent is idle, how often a bored interruption comes around |
| `boredMs` | `5000` | How long each bored interruption lasts |
| `sleepAfterSeconds` | `600` | Seconds without activity before it sleeps, while DSH is on screen |
| `sleepWhenHiddenSeconds` | `20` | The same once DSH is tucked away, where dragging the pet is the only activity |
| `autoHide` | `true` | Never while DSH itself is in front; whether going behind another application tucks it away |
| `autoHideSeconds` | `0` | How long DSH may stay behind before that tuck; `0` tucks it at once. A running task does not postpone it |
| `topmost` | `true` | Whether the pet stays above other windows |
| `clickAction` | `toggle` | `toggle` / `minimize` / `none` |
| `gitPullTimeoutMs` | `60000` | Upstream-check and pull deadline in milliseconds, from `1000` to `300000`; configurable in the profile even though the custom card has no control for it |
| `shotDir` | *(empty)* | Folder the menu's screenshots are written to. Empty keeps them in the plugin's own `$DSH_HOME/little-icon/shots/`; `~` expands to the user directory and a relative path is relative to it, so the folder does not depend on where DSH was started |
| `sites` | `[]` | Entries the right-click menu's Sites submenu lists, in array order, each `{ "name": note, "url": address }`. A row whose `url` is empty, is still not HTTP/HTTPS once `https://` is added, or carries a user name and password never reaches the menu; a blank `name` uses the address's host. The card has the matching editor |
| `musicLinks` | `[]` | Bilibili addresses the listening library is built from, in the pet's play order. The same mechanism copies the field into the repository's `pet-settings.yml`, so the repository carries the links and never the audio; the card has the matching paste box and list |
| `musicDir` | *(empty)* | Folder the audio files are downloaded into. Empty keeps them in the plugin's own `$DSH_HOME/little-icon/music/`; `~` expands to the user directory and a relative path is relative to it. A directory inside the checkout is ignored in favour of the default one (reported as `inside-checkout` on the card), and changing this value does not move files already downloaded |
| `musicVolume` | `70` | What the pet plays at, `0`–`100`. It travels in the settings file, so both machines share it |
| `coopAddress` | `192.168.1.3:15180` | Host address, `IP:port`. Whichever machine has a network adapter on that IP is the host and listens on that port; the other is the client and dials in. Both machines share this one value, and it is the only field to edit when the host's IP moves |
| `coopHotkey` | `ctrl+alt+f12` | Hotkey the host uses to switch between this computer and the remote one |
| `coopAutoStart` | `true` | With this on, starting DSH brings the multi-machine link up at `coopAddress` on its own, with no menu entry to choose. It follows the **Enable the pet** rule: only the switch's own transition acts — on starts the link, off ends it — and a link **stopped from the menu** is not restarted by any other settings write, only by the next DSH start |

**Pull behavior.** `POST /api/little-icon/git/pull?cwd=<Session working directory>` resolves the repository and upstream, then runs `git pull --ff-only` with credential prompts disabled. Requests for the same repository join one in-flight operation instead of competing for Git's locks. A successful answer includes the refreshed changes and commits plus whether `HEAD` moved; failures preserve the page's existing state. Git subprocesses do not inherit environment variables whose names contain `KEY`, `SECRET`, `TOKEN`, or `PASSWORD`.

**State to expression.** One run reads as `working` right away (no startle first) → `alert` (startled) while it waits for your decision, held for as long as the question stands → `happy` when it ends → `idle`.

- **Listening** is layered on the sampled expression instead of being sampled itself: the pet's player is the input, so while audio plays the listening frames (`music`) stand in for the idle family — `idle`, `bored`, and `sleep` — while the run's own faces (`working`, `alert`, and the `happy` celebration) keep theirs. Pausing or stopping returns the sampled expression at once.
- **Boredom** follows whether a task is running rather than the mouse: while the agent is idle, `bored` interrupts every `boredEverySeconds` for `boredMs`, so a long answer still shows it now and then, and any activity ends the current interruption.
- **Sleep** follows activity, on two timers. While DSH is on screen it takes `sleepAfterSeconds` without pointer, wheel, or keyboard input on the page, a drag of the pet, or a click on it — any of those wakes the pet into idle at once. Once DSH is **tucked away**, the `sleepWhenHiddenSeconds` timer applies (20 seconds by default), where the only possible activity is dragging the pet or bringing DSH back by clicking the pet.
- **It holds the startle while it waits on you.** While a question with options or an approval is unanswered, the pet switches to `alert` (startled) and **keeps it up until you answer** — that is the "it is your turn" signal, and it reads even while DSH is tucked away. The host observes the `user-questions/request` and `approval/request` waterfalls (observation only, always delegating with `next()`) and notes the agent waiting for the user: that agent is not working then, and the pet does not fall asleep inside the run, because the person is what it waits on. The answer returns it straight to `working`, with no second startle. Input queued behind that question is not work either, since the person answers first.
- **Tucking DSH away behind another app** (`autoHide`, on by default) reads who is in front rather than whether anything happened: DSH itself in front is never tucked away, so a long answer no longer disappears while you read it. Once another application comes to the front — your editor, your browser — the pet tucks DSH away, and `autoHideSeconds` (0 by default) is the grace period after that switch, with 0 meaning the next sample. **Whether a task is running makes no difference** — the task keeps going, the window goes first. This only ever applies while DSH is still on screen; a minimized or already tucked window is left alone. DSH's own dialogs and update prompts, and the pet's own window, all count as DSH's side, so dragging the pet never tucks DSH. Clicking the pet (or DSH's own tray icon) brings DSH back and makes it the front window in the same step, so it is not tucked again immediately.

The pet writes whether DSH is on screen and whether it is DSH's side that is in front (its main window, one of its dialogs, or the pet itself) into `window.json`: the first selects the sleep timer, the second decides the auto-tuck, and a change in either counts as activity by itself. Each state is a four-frame loop.

Local data lives under `$DSH_HOME/little-icon/`: `state.json` (written by the host, read by the pet — besides the expression and size it carries a `notice`: the last "open working directory" that opened no folder, with its timestamp — the absolute `shotDir` the screenshots go to, which is absent while that setting is empty — and the `sites` the menu lists), `position.json` (written by the pet), `window.json` (the pet's report of whether DSH is on screen and whether it is in front), `command.json` (the pet's right-click menu choice, which the host reads and relays to the page), `shots/` (one timestamped PNG per screenshot the menu entry took, unless the `shotDir` setting moved them elsewhere), `music.json` (written by the host, read by the pet — the absolute path of every track, the volume, how many links still have no file, the progress of a running fill-in, and the command or notice meant for the pet), `music-player.json` (written by the pet: what it is playing, the position in milliseconds, and the timestamps of the commands it has applied, which the host reads for the card), `music-index.json` (this machine's id-to-file index), `music/` (the audio files themselves), and `quit` (the host's "please exit", which the pet answers by storing its position and closing its own window in order, taking the request with it). It is per machine and never syncs with the repository; deleting it restores the default position and state. The **settings** are not in this directory: the pet's own row travels through git in [../../settings/pet-settings.yml](../../settings/pet-settings.yml), the Desktop's shortcut document travels in [../../settings/keybindings.json](../../settings/keybindings.json) from its userData directory, and `build\start-desktop.bat` (or a restart from the pet's menu) writes both back into each machine.

## Understand the implementation

<details>
<summary>Implementation details — click to expand</summary>

**Why a separate process is required.** The desktop shell exposes no window capability to plugins: the main window's `BrowserWindow` sets neither `transparent` nor `alwaysOnTop` nor `skipTaskbar`, `apps/desktop/src/ipc.ts` lists no minimize/hide/restore channel, and `preload-app.ts` exposes only `dshDesktop` (browser views and updates), `dshPlatform` (the usage/top-up embedded page), the directory picker, host paths, and the locale. The shell does own a tray icon of its own (`apps/desktop/src/tray.ts`), but a plugin cannot add entries to it or draw in it. The renderer runs with `sandbox: true` and `contextIsolation: true`, and `window.open` is denied outright. Decisively, plugin host code runs in the `ELECTRON_RUN_AS_NODE=1` Node child process (`apps/desktop/src/host-process.ts` plus `node-environment.ts`), where `require('electron')` yields the binary path and nothing more. A hidden window stops painting its DOM as well. "The pet stays after DSH is tucked away" therefore needs a process the plugin starts itself.

**Browser half.** `client.js` does four things. It registers a hand-written settings card into `plugins.bundle.config`, the seat the Plugins page keeps for one bundle's own configuration, keyed by the package name `@local/dsh-little-icon` — drawn right on the plugin list's card page, one click shallower than the `little-icon` row's own page. The card reads no configuration itself: `ctx.configForms.get('little-icon')` yields the row's form, whose accepted sections are mirrored into a snapshot store and handed to the component through the registration's inject face (`hooks.petSettings` plus a `write` callback), so the Host schema stays the single owner of every value. Sliders echo locally while dragging and collapse into one write 250ms after the drag settles; switches and the select write at once, and the screenshot folder is a text box that echoes while it is typed and writes once it is left — one profile write per keystroke would be one per character of a path. Beside it the **Browse** button fills the field from the same directory picker the workspace panel opens (`ctx.get('uiWorkspace')?.pickDirectory()`, looked up rather than injected and answered with nothing when this build has no picker), and a cancelled picker changes nothing. The host half therefore calls `settings.configure({ auto: false })`, so the same fields never appear twice in a generated English form. Second, it reports user activity (next paragraph). Third, it performs the pet's right-click menu commands: it subscribes with `new EventSource('/api/little-icon/commands')` and, on `chat` or `site`, opens the address at **the destination the person chose, not one this plugin hard-codes**: `linkOpening` from `ctx.configForms.get('ui-chat')`, the value `ui-chat` itself reads for a conversation link. `sidebar` with a Browser tab in this build calls `ctx.sidebarRight.openTab('browser', { params: { url } })`, the seat a plugin opens a site in; everything else goes to `window.open`, which the Desktop main process turns into the system browser. The value is read at the click and never mirrored, so an edit on Chat's settings page applies to the next menu choice. That address is checked in all three places it passes through (the pet writing `command.json`, the Host relaying it, the page opening it): both later halves accept only HTTP/HTTPS with no credentials, the Host leaves a refused address out of the frame, and a page handed a `site` command with no address only logs a warning, so no entry ever reaches the menu that would open nothing. `sidebarRight` and `sidebarRightTabs` are looked up through `ctx.get` rather than injected (a Web profile may leave the `browser` type disabled, and a build without the right Sidebar provides no service at all); when either is missing the preference still names the in-app tab, so the address falls back to the system browser with a `console.warn` saying why, because this card has to load in every profile. The stream's `open-cwd` command is the other kind: it takes the `cwd` of the Session the main view holds — the same row DSH's own "open workspace" control reads — and `POST`s it to `/api/little-icon/open`, then stays out of it, because opening a folder is the Host's job and saying that none opened is the pet's. `settings` is the third kind: nothing of this plugin's own is opened at all, because the card is drawn on the plugin manager's page, so the command reaches that page's navigation service (`ctx.pluginNavigation.openBundle`) — looked up through `ctx.get` like the Sidebar, since a build without the Plugins panel provides no such service — and only logs a warning when it is missing. The `aquarium` command is the one that opens **another plugin's** surface: it takes `ctx.get('aquarium3d')`, the service the 3D glass aquarium plugin provides, and calls its `open()`, so that plugin owns how and where the tank is drawn, and a profile without it logs a warning too. All copy lives in `ctx.locale` dictionaries (Chinese and English); `tests/smoke.mjs` asserts the two cover the same keys, that the card asks for nothing else, drives one immediate write and one merged drag through the real form API, holds a path box that writes only when it is left and a picker that writes what it answered, checks that the activity listeners register and throttle, drives a `chat` command plus both unavailable-service paths, an `open-cwd` command in its three forms (a main-view Session, no main-view Session, no sessions service), a `settings` command with and without the Plugins page's navigation service, and the `EventSource.close()` that disposal performs, and renders the Git page from a seeded repository answer. It also renders the state a double-click leads to, asserting that the detail replaces both columns, that the Back button is what returns, that every diff line carries its own tone, that a commit's rows carry the listing's status words with a rename showing its source, and that an empty, truncated, or failed read each says so in the detail's own place. Fourth, it provides the **Git page**: the `git` command calls `openTab('little-icon-git')`, and that page type is one this plugin registers itself, through the right Sidebar's own two stages — `ctx.sidebarRightTabs.register({ id, kind, title })` says what the type is, and a component registered under the same `id` in the keyed `sidebar.right.pane.tab` seat draws its body. The registry admits types from outside the product by design, so the page needs neither the Browser tab nor any shipped viewer; the whole registration hangs off `ctx.inject(['sidebarRightTabs', 'slots'], …)`, which never runs in a build without a right Sidebar while the settings card above still loads there. The component reads no file: its inject face supplies three reads — `load(cwd, signal)` over the Host's Git route, `loadDiff(root, path, signal)` for one file's diff, and `loadCommit(root, hash, signal)` for one commit's files, the last two carrying the repository root rather than the Session's directory because the path the listing gave is relative to that root (the Host is what looks a path's status up, and what asks for a commit's parents, before deciding which comparison to run) — while `useSessions` supplies the current Session's working directory and `useTabInfo` supplies this navigation's `revision`, so choosing the menu entry a second time re-navigates the same tab and refetches, which is the same path the Refresh button takes. Opening a row's detail is a state in that component: a set `detail` replaces both columns, draws a diff or a file list from its `kind`, gives each kind its own header, and the Back button sets it back to `undefined`, so the listing is never fetched again just to come back. The same face's `sendPrompt(text)` is what the **Commit and push** button calls, and it borrows the Session's own scope to reach `ctx.conversation.send` — the composer's admission, not a private channel: a Session nobody holds resolves no scope and answers `no-channel` instead.

**Where "activity" comes from.** The Host sees agents and jobs, and "nobody has touched anything" is not the same as "no task is running" — without an input signal the pet would sleep while the person keeps using DSH. The browser half therefore pings `POST /api/little-icon/activity` on `pointerdown`, `pointermove`, `wheel`, and `keydown`, throttled to one every 15 seconds. That route is same-origin, checks `connection.requestRejection` first like the repository's own routes, and answers 405 to anything but POST. The Host takes the newest of that timestamp and the pet's `position.json` modification time, so dragging the pet counts too. A tucked DSH window produces no page input at all — which is the point — so there the pet reports the window state it alone can see into `window.json` once a second (on screen, and whether DSH's side — its own windows or the pet — is what is in front), and the Host switches timers on it and decides the auto-tuck from it. Showing, hiding, or moving to and from the front counts as activity on its own, which also starts the tucked sleep timer the moment the auto-tuck lands. Sleep therefore arrives only after a stretch in which nothing at all happened, and starting a task counts as activity as well.**Why the pet does not count the inbox.** A message waiting in an inbox is input nobody is processing, not work under way: when a background job settles, DSH injects `background job … finished` into the owner's next-step, and under a quiet delivery (or a spent wake budget) it waits there for a step that may never come. Computing that the way `update-tasks.ts` does — it answers "would stopping now lose something?" — left the pet on **working** while nothing ran at all, which is the bug this rule fixes: busy means an agent is generating; jobs and queued input are published in `work` but do not drive the face. The state file therefore carries `work: {agents, jobs, queued}`, so a stuck face explains itself.


**Host half.** `index.js` samples every `pollMs`: `ctx.get('agents')` for an agent that is generating or running tools (a job does **not** drive the face: every tool call runs as one, and a call whose child outlives it — a dev server left running, a detached helper — stays `running` indefinitely), minus the agents blocked on a human answer: the host prepends an observer to the `user-questions/request` and `approval/request` waterfalls (delegating with `next()` itself and returning the chain's own promise) and leaves the asking agent out of the busy set while reporting it as `waiting`, which is what the state machine turns into a held `alert`; it returns to normal when the answer settles, so "the model is waiting for you to choose" is neither read as work nor missed. The decision itself is the pure `sampleState`, which `tests/smoke.mjs` drives directly; it takes "is anything running", "when did anything last happen", and the sleep timer currently in force, which the reported window visibility selects. A second pure function, `shouldTuck`, decides whether DSH should be tucked away: it sees only the window facts the pet reports — on screen, whether somebody else is in front, and when DSH went behind — plus `autoHide`/`autoHideSeconds`. DSH itself in front returns false outright, so a window you are looking at is never taken away, and "is a task running" is deliberately not an input, so a task keeps going while the window goes. Its answer is published as `tuck` in `$DSH_HOME/little-icon/state.json`, which is a command rather than a state: the visibility the pet reports back turns it off on the next sample, and a repeat of the same request in between is harmless because the pet's own window setter is idempotent. The file is written on change, plus a four-second heartbeat the pet uses to tell whether the host is still alive. Writing means a temporary file replaced by a rename, and Windows refuses that rename while any process has the file open — which the pet's own 200 ms read of state.json does — so the writer retries; a snapshot that still cannot be placed leaves the previous one in place, reports the error (at most once per 30 seconds while writes keep failing), and waits for the next sample. Nothing escapes: the harness exits the whole host process on an uncaught exception (the 2026-09-27 crash was this rename reporting EPERM), so the sampling tick and the publish a settings change triggers both run behind the same guard. `translucent` and `idleOpacity` collapse into one `opacity` field here, so the pet needs no notion of the switch. The pet is started with `child_process.spawn` (`powershell.exe -NoProfile -NonInteractive -STA -ExecutionPolicy Bypass -File pet/pet.ps1`) carrying the asset directory, the state and position files, and the process id of the window to control; the `ctx.effect` disposer ends it (asking it to quit through the `quit` file first, so it stores its position and closes its window in order, and killing it only if it does not answer within a second), so DSH leaves no orphan window. In the desktop shell the host's parent is the Electron main process, so that id is simply `process.ppid`; the web profile has no window to control and passes 0. Menu commands take another route: the pet writes its choice to `command.json`, the host reads that file once per tick (only a strictly newer `at` counts as a new command, so a record left by a previous run is never replayed) and pushes it to the page over the `GET /api/little-icon/commands` SSE stream. A `site` record also carries a `url`, which the host accepts only when it is HTTP/HTTPS with no credentials before putting it in the frame — a file is a file, whatever wrote it — and the `sites` the menu lists travel in the same sampling snapshot, where a row the Browser tab could not open is dropped before the pet ever sees it. That stream passes the same `connection.requestRejection` check as the activity route, answers with nothing but the event stream (`text/event-stream`, opening with a comment frame so a subscriber is live at once), and is dropped from the subscriber set and `end()`ed when the client disconnects or the plugin is disposed. A command chosen while no page is listening is dropped: the page is what performs it, so with no page there is nothing to perform it.

**Git route.** The Git page's facts live on disk and the page has neither a filesystem nor a process, so the Host asks Git for them: `GET /api/little-icon/git?cwd=<Session working directory>` answers one JSON object. It confirms the directory exists first (`statSync`), because `execFile` cannot tell the two cases apart — a missing directory and a missing `git` both fail to spawn with `ENOENT`, and the page says different things about them — and then resolves the repository root with `git rev-parse --show-toplevel`. The directory finds the repository rather than the other way round, so a Session started in a subdirectory still reports the whole repository. Four read-only commands follow, concurrently: `branch --show-current` (empty on a detached HEAD, where the page then shows no branch), `status --porcelain=v1 -z --untracked-files=all`, a `log` for one page of commits (ten rows, plus one more that says whether the history continues, its fields separated by `0x1f`), and `shortlog -sne HEAD`, the authors of this history with each one's commit count — which is what the filter offers. The `status` and `log` outputs are parsed as `-z` records, so NUL separates them and no punctuation in a commit subject can collide with a separator; a rename or copy carries its source path in the record that follows, which is why that walk advances by hand. A repository whose first commit has not been made yet makes `git log` fail, which is a normal state answered with an empty list rather than an error. The route accepts GET only and always answers 200 JSON: a missing directory, a directory outside every repository, a missing `git`, and a failed command are the four reasons `no-dir`, `not-a-repo`, `no-git`, and `failed`, which the page turns into words — machine-readable reasons rather than localized copy, because only the page knows which language to use.

**Git remote route.** `POST /api/little-icon/git/remote?root=<repository root>` resolves the current branch's configured remote, remote branch, and remote-tracking ref, then fetches only that branch into its tracking ref with `--no-tags --no-write-fetch-head`. It compares `HEAD` with the refreshed ref through `rev-list --left-right --count` and returns `up-to-date`, `behind`, or `diverged` plus both counts. Checks for the same repository and tracking ref share one in-flight request, while every fetch and pull for a repository is serialized so the two actions cannot compete for ref locks. The route uses POST because the fetch updates a remote-tracking ref, even though it never moves the local branch, index, or working tree. Its unavailable states distinguish a detached HEAD, a branch without an upstream, a timeout, and a Git failure.

**Git diff route.** Double-clicking a row asks the Host once more: `GET /api/little-icon/git/diff?root=<repository root>&path=<the row's path>`, GET only and always 200 JSON like the listing, through the same guard and the same JSON writer. It confirms the directory and resolves the repository the same way, so "the directory is gone", "not a repository", and "no `git`" get the listing's own answers here too. It then looks the path's status up itself (`status --porcelain=v1 -z --untracked-files=all --`, with the path wrapped in `:(literal)` so a `*` in a filename is not read as a glob) and runs only the comparisons that have something to say: `diff --cached` when the index side holds a change, `diff` when the worktree side does, both blocks one after the other when both do. An untracked file is compared against `NUL` on Windows and `/dev/null` elsewhere through `diff --no-index`, whose exit code 1 means "they differ" rather than failure — the diff is on stdout either way. `HEAD` is never the other side of a comparison: it does not resolve in a repository with no first commit, and `--cached` already compares the index against the empty tree there. Every call carries `--no-color --no-ext-diff`, so a configured color or an external diff driver cannot put escape codes or another program's output in the page. Text past 200,000 characters is cut and the answer says `truncated: true`, which the page states on the diff's own first line. When the path was committed or reverted between the two commands, the status query reports nothing and the answer is an empty diff (`{ok:true,text:''}`) — the page says there is no diff to show, which is a normal state rather than an error.

**Git commit route.** Double-clicking a row in the history column asks `GET /api/little-icon/git/commit?root=<repository root>&hash=<that row's full hash>`, GET only and always 200 JSON like the others, with the same directory and repository checks up front so all three "cannot read it" answers read the same way. A commit has no working tree to compare against, so its paths come from `diff-tree`, and its parents are asked for first with `rev-list --parents -n 1 <hash>`: **the first commit has none**, so the empty tree is the other side through `--root` (`diff-tree` lists no file at all for it otherwise), and **a merge has more than one**, so the first parent is what it is compared with (`diff-tree` given only the merge itself lists nothing either) — which is why a merge shows what it brought in. A hash Git does not have makes `rev-list` fail, and Git's own words travel back as `failed`. The output is parsed as `-z` records: the status first, then the path, with `R100`/`C075` the only statuses carrying two paths, source before destination — the page shows the destination as the path and the source beside it as "← old path". An empty commit answers with an empty list, which the page states in a line.

**Git commits route.** Scrolling the list to its end, or choosing an author, asks `GET /api/little-icon/git/commits?cwd=<Session working directory>&skip=<rows already shown>&author=<author identity>` — GET only, always 200 JSON, behind the same guard. It names the **directory** rather than the repository root because the Host resolves the repository exactly as it did for the listing: a workspace that moved between two pages is answered about the repository that is there now. A `skip` that is not a safe integer or is below `0` reads as `0`; an empty `author` is every author, and otherwise the value is one of the identity strings the listing itself handed out. The route runs the listing's own `log` (same field separator, same extra row, same `--skip` and `-n`) with one addition, `-F --author=<identity>`: **`-F` is what makes it correct**, because `--author` reads its argument as a basic regular expression by default, where an address like `second+tag@example.test` is a quantifier that matches another commit or nothing at all. As a fixed string it matches the identity the listing gave out, and only that one. Reading past the end (`--skip` beyond the history) answers with an empty page rather than an error, which is how the page knows it has reached the beginning.

**Music routes.** The card can neither list a directory nor reach Bilibili, and the pet's own menu must work with no page open, so the Host owns both halves: `GET /api/little-icon/music` answers the library view (this machine's links, the entries with files, the directory and its warning, the volume, the progress of a running fill-in, and what the pet reports it is playing); `POST /api/little-icon/music/sync` starts filling in every missing link in the background and answers the count it started; `POST /api/little-icon/music/download?url=` takes one address and answers once the file is on disk; `POST /api/little-icon/music/expand?url=` answers every link one pasted link stands for, together with the subset the settings do not already hold, so a collection is one paste and a song it already has is still one row; `POST /api/little-icon/music/added?count=` records that a set arrived, which is what the pet says above itself, because a set is added without being downloaded; `POST /api/little-icon/music/remove?id=` deletes the entry and its file — `?ids=a,b,c` does the same for a whole set in one request — answering `busy` while the pet is playing that file; and `POST /api/little-icon/music/command?action=play|pause|toggle|next|prev` writes a command for the pet. Every route runs behind the same connection check and method guard as the Git ones, and a download or a fill-in does not need the page to be listening: the pet's menu reaches the same work through `music-sync` and `music-open-dir` in the command file, which is also why the card's transport buttons write into `music.json` instead of playing anything themselves.

**Open working directory route.** `POST /api/little-icon/open?cwd=<Session working directory>` is the one route here with an effect outside the page, so it is also the one that refuses GET: re-reading a listing must never open a folder. It looks at the directory first — an empty `cwd` answers `no-cwd`, and a path `statSync` does not call a directory answers `no-dir` — rather than letting the file manager hit it: a shell handed a path that is gone opens a different folder or a dialog of its own, which reads as the wrong folder rather than as a refusal. Only then does it `spawn('explorer.exe', [directory], { detached: true, stdio: 'ignore' })` and `unref()` it; Explorer is the shell itself, so the path is handed to the window that is already open. A spawn failure arrives after the route has answered, which is why the `error` listener is attached (an unhandled `error` event would take the whole host down) and why only the log hears about it. The three failure reasons (`no-cwd`, `no-dir`, `failed`) do not stop at the page: each one is published into the state file as `notice: { at, reason }`, because the click happened on the pet and the pet is the half with a place to say it. `at` is what keeps it to one message — a notice that has not moved neither reappears nor causes another write. `tests/smoke.mjs` drives this route through a host instance with `enabled: false`, so no real pet is started and no folder window or message box lands on anybody's desktop: GET answers 405, both refusals answer in their own words, and the `notice` really is in `state.json`. The success path is driven separately through `openWorkingDirectory` with an injected launcher.

**Pet process.** `pet/pet.ps1` is a WPF frameless transparent topmost window (`WindowStyle=None`, `AllowsTransparency`, `Topmost`, `ShowActivated=false` so it never steals focus). The script declares the process DPI aware first (`SetProcessDpiAwarenessContext`, falling back a step at a time): PowerShell has no DPI manifest, and a layered window in an unaware process is rendered into a surface at the virtualized size and then stretched by the system, which tiled the pet two-by-two and drew it larger than asked. After `WindowInteropHelper.EnsureHandle()` it adds `WS_EX_TOOLWINDOW` to the handle, because WPF's `ShowInTaskbar=false` does not actually set that style and the pet would otherwise appear in the taskbar and Alt+Tab. A 200ms timer re-reads the state file when its write time moves, applying expression, size, opacity, click action, and topmost; frames advance every `frameMs`, and the script counts the frames on disk instead of reading a constant (most states have four, `working` has six). Dragging uses `DragMove()`. The press that activates the pet window is reported twice — once while WPF handles the activation, once as the ordinary mouse message — and that first report cannot start a drag, so a press only latches and the release decides click or drag; acting on the first report would run the click action twice and tuck DSH on a press that only dragged the pet. The position is stored in `position.json`, restored at start, and clamped onto a screen. The right-click menu (`New-PetMenu`) is the plugin's only menu, a WinForms `ContextMenuStrip`: on Desktop the first entries are **Chat** and **Sites** — the latter a submenu listing the configured sites — then **Git changes**, which each call `Show-DshWindow` to restore and raise DSH (`SW_RESTORE` when it was tucked away or minimized, `SetForegroundWindow` when it was merely behind) and then write `{"command":"chat","at":…}`, `{"command":"site","url":…,"at":…}` or `{"command":"git","at":…}` to `command.json` for the host to relay, the next is **Open working directory**, which only writes `{"command":"open-cwd","at":…}` there — it raises nothing, because the folder window is what the person asked to see — then **Screenshot**, which is this process's own work and writes no command at all, and the menu closes with **Settings**, which raises DSH like Chat and writes `{"command":"settings","at":…}` for the page to open the Plugins page on this bundle's card. **Sites** is the one entry whose contents come from configuration: `Update-SiteMenu` rebuilds it whole from the published `sites` whenever the submenu opens (`Add-SiteMenuItem` is called once per entry and pins that entry's site into its handler with `.GetNewClosure()` — a PowerShell script block resolves variables from the scope in force when it **runs**, not the one that made it, so both a shared handler in a loop and a handler reading the function parameter directly see nothing at the click and write the command with no address; `tests/smoke.mjs` fires one entry with `PerformClick()` to keep that honest), which is what lets a card edit reach a running pet; an empty list gets one disabled line saying so, and **Manage sites** closes the submenu with the `settings` command. When the host reports that nothing opened, the pet reads the `notice` in the state file and says so in a box (`Get-OpenFailureText` maps the host's `no-cwd`/`no-dir`/anything-else onto the words in labels.json, and one `at` is shown once); the web profile has no system window to control, so the **System** submenu below the divider — update, restart, and quit — is not built there, and the pet's own menu no longer carries tuck/show or move-home at all. The foreground fact it reports every second means "DSH's side is in front": windows of DSH's own process (dialogs, the update prompt) and the pet's own window all count, and only a third-party application in front counts as being behind — so dragging the pet is never read as your having moved to another application. Every label is read from `pet/labels.json` as UTF-8, with English defaults inside the script, which itself stays pure ASCII.

**Restarting DSH.** In the **System** submenu, the entry above **quit DSH** is **restart DSH** (it asks first too, since a restart interrupts whatever is running), and what it does is "end DSH, then start it again the way it was". That cannot happen inside the pet: ending DSH unloads the plugin, whose cleanup ends the pet with it, so a **detached waiter** (a hidden `powershell.exe -EncodedCommand`) is armed first — it waits for the DSH process to really exit, waits four more seconds for the Host's shutdown (sessions flushed, agents stopped), and then acts. What the waiter replays is "how DSH was started", which only that process knows, so it reads its command line from WMI (`Win32_Process.CommandLine`) and hands it to `cmd /c` verbatim; the line never passes through a command line of our own but travels in the `DSH_RELAUNCH_CMD` environment variable for cmd to expand, so spaces, quotes and non-ASCII paths are not re-parsed by any layer in between. The working directory is **the last quoted token that names a directory**, which is what the launcher uses as its work directory (`start-dsh-service.vbs` sets `CurrentDirectory` to the application directory). **This replay does not pass through `build\start-desktop.bat`**, so the pet also runs the settings merge that launcher would have performed before starting: it executes `_mytools\settings\sync-pet-settings.mjs apply` first, locating the repository through that same `apps/desktop` anchor, and a missing `node` or a failed merge is only logged rather than allowed to block the restart. One environment trap is worth naming: the pet runs under the Host, which runs under Electron in Node mode, so the whole tree carries `ELECTRON_RUN_AS_NODE=1`, and an Electron started with it runs as a plain Node process and dies on the app's first import — the waiter drops it before starting anything (only there; the pet itself still needs the environment it was given). When the command line cannot be read (no WMI), **DSH is left alone** and a message says so: doing nothing is better than ending it with no way back. Any failure while preparing the restart reports itself in a box too, saying DSH was not touched — including the one that was found the hard way: in Windows PowerShell a computed name cannot be assigned through `$env[$name]` ("Cannot index into a null array"), and because that happens *before* DSH is ended, it looked exactly like a menu entry that does nothing. That variable is now set through .NET, and a failure there speaks instead of staying in the log.

**Updating DSH.** The Desktop-only **Update DSH** entry builds the current checkout; it does not fetch or pull code. After confirmation, the pet locates `_mytools/build/build-desktop.bat` from the running `apps/desktop` directory and invokes it with `--detached --restart`. The detached console shows each build line as it arrives and mirrors it to the log; it closes on success, while a failure leaves the final output and log path visible until Enter. The detached build records its result under `$DSH_HOME/build`, closes this checkout's Electron process before cleaning, and runs `start-desktop.bat` only after every Desktop build and preparation step succeeds. A preflight or dependency failure leaves DSH running; the pet re-enables the entry and reports the failed step and log path. A failure after the build closes DSH stays closed for inspection instead of starting a partial result. If the running command line does not identify this checkout or the launcher cannot start, DSH remains running and the pet reports the failure.

**Geometry units.** Position and clamping use WPF's own `SystemParameters.WorkArea` and `VirtualScreen*`, which share the device-independent units of `Window.Left/Top`. WinForms reports the work area and virtual screen in physical pixels, and mixing the two pushes the pet off-screen at any display scaling other than 100% — a bottom-right position lands 1.5x too far right and down at 150%. `tests/smoke.mjs --pet` measures the window from a DPI-aware probe and asserts it is inside the screen.

**Window control.** The target starts as `Process.MainWindowHandle` — the real main window, which the untitled helper windows cannot confuse, so it is trusted first. When that reports 0 (a hidden window), the pet enumerates the process's top-level windows and skips IME helpers such as `IME`, `CandidateWindow`, and `MSCTFIME UI`. The handle is cached, because `MainWindowHandle` becomes 0 after `SW_HIDE`. Tucking uses `SW_HIDE` (gone from both the screen and the taskbar, leaving the pet and DSH's own tray icon as the way back); bringing it back picks the command by the state the window is in — `SW_RESTORE` for a minimized one, `SW_SHOW` for one this pet merely hid. The two are not interchangeable: `SW_RESTORE` also returns a maximized or fullscreen window to the size and position it had before, which is how tucking DSH away and showing it again used to drop it out of fullscreen (measured: a hidden maximized window comes back un-maximized under `SW_RESTORE` and maximized under `SW_SHOW`), while `SW_SHOW` in turn does not bring a minimized window back — so only the minimized case is restored (`Get-ShowCommand` is that decision, and `-SelfTest` prints it to hold it). Both are followed by `SetForegroundWindow`. Every change goes through one `Set-DshWindowShown`: a click, a menu entry, and the host's `tuck` request all use it, and it returns when the window is already where it was asked to be, so a repeated `tuck` never brings a just-tucked window back; `clickAction`'s `minimize` still uses `SW_MINIMIZE` on its own. **Whether a click hides or raises** is `Get-ClickIntent`'s decision: only a window that is both on screen **and** the one in front is tucked away, and everything else goes through `Show-DshWindow`. The second fact comes from `Get-DshInFront`, deliberately stricter than `Get-DshForeground`: only a foreground window belonging to DSH's own process counts, because the press itself makes the pet the foreground window — counting the pet the way the host's auto-tuck question must would answer "in front" for every click and DSH could never be tucked away again. That fact is sampled **before** the click (on mouse enter, and in the once-a-second window sampling), never while handling it.

**Encoding.** `pet.ps1` stays pure ASCII: without a BOM, Windows PowerShell 5.1 decodes a `.ps1` as ANSI, which turns UTF-8 Chinese into mojibake and can even swallow quotes into a syntax error. The localized menu labels live in `pet/labels.json`, read as UTF-8, with English defaults when it is missing. `tests/smoke.mjs` asserts the script contains no non-ASCII character.

**Art.** `assets/<state>/1.png … N.png` come from `tools/build-assets.py`, which slices one sprite sheet per expression; the finished frames are the only copy of the art in the repository (the ~24 MB of source sheets were deleted — restore them from git history as the dev note below describes). Each source sheet packs several figures onto one 2048×2048 canvas, and the layouts differ: most states are two-by-two (four figures), `working` is three columns by two rows (six), and `sleep` leaves only 14 transparent pixels between its rows. The script therefore assumes no grid and finds figures by alpha projection: empty rows split the sheet into bands (a gap under 8 pixels does not split, and bands too short to be a figure are absorbed into their neighbour so Zzz bubbles and gear icons stay attached), column valleys below 12% of the band's peak split each band into figures, and each region is then cropped to its actual opaque pixels. Figures run top-to-bottom, left-to-right, are pasted bottom-centered onto one shared canvas per state, and share a single global scale taken from the largest figure in the set, so a state never jumps between frames and the character keeps its size across expressions. The artwork decides the frame count, recorded in `assets/frames.json`; the pet counts files rather than reading a constant, so new art needs no code change.

<a id="model-experience"></a>
## Model experience

None. The plugin adds no model-visible input, prompt, tool, or session event; it only reads agent and job status.

## <a id="known-limitations-and-deferred-work"></a>Known limitations and deferred work

**Errors have no expression of their own.** `agent/error` is still in the event table, while `alert` now belongs to waiting for your decision (above). Giving failures a face again is a matter of listening for that event in the host half, feeding the state machine one more input, and having the art for it.

**Activity comes only from the DSH page and the pet itself.** The report is built from input events on the DSH page, so a tucked, minimized, or covered DSH window produces none: while tucked the pet sleeps on `sleepWhenHiddenSeconds`, which is the point. Working in another application does not keep it awake; typing or clicking back in DSH, dragging the pet, or using the menu's move-home entry does.

**"Tuck away" uses `SW_HIDE`, not minimize.** The DSH window leaves the screen and the taskbar; the way back is the pet itself and the tray icon DSH's own main process keeps (`apps/desktop/src/tray.ts`: click to open the window, right-click for Open application / Quit application). The pet builds **no** `NotifyIcon` of its own: the notification area already holds one icon that belongs to DSH, and a widget hanging off DSH should not add a second. If DSH exits some other way, the pet quits on its own within 45 seconds or as soon as the host process is gone.

**Quitting the pet asks first and kills only as a fallback.** The host does not kill it outright: it writes the `quit` file, which the pet reads within one 200 ms tick (storing its position, closing its window in order, and taking the request with it), and only a pet that does not answer is killed, one second later. That keeps a normal teardown from racing the position file the pet is still writing. `tests/smoke.mjs --pet` covers both halves of that handshake: starting a pet must clear a `quit` left by a host that died mid-teardown (or the new pet would quit on its first tick), and switching **Enable the pet** off writes the request, which the pet answers by exiting and taking the request with it.

**The in-app browser does not sign in by itself.** **Chat** and **Sites** open DSH's right-Sidebar Browser tab, whose storage partition is persistent (the one upstream file this working copy changes: `apps/desktop/src/browser-guests.ts` names it `persist:dsh-sidebar-browser-<digest of the workspace identity>`; the edit, the rebuild, and the restore steps are in [UPSTREAM.md](UPSTREAM.md)), so signing into chat.deepseek.com there once keeps you signed in across DSH restarts. A **rebuild** keeps it too: `--user-data-dir` now points at `$DSH_HOME\desktop\electron-user-data`, outside the `.desktop-build` tree `pnpm run clean` deletes (see the migration note in the working copy's `_mytools/README.md`). The key is the **workspace**: a Session that belongs to one is `cwd:<path>` (stable, shared by a restart and by every conversation in it), while one that belongs to none falls back to `session:<conversation id>` — a new conversation is a new partition, and the sign-in with it. It is not, however, signed in with the DSH account: the credentials DSH holds belong to `platform.deepseek.com` (`platform-view.ts` injects them for that origin only, which is what makes the official usage page work), while chat.deepseek.com runs its own Web session — and a plugin cannot put cookies into that partition either, because the host half has no Electron API, the browser half is sandboxed, and the partition belongs to `apps/desktop`. DeepSeek also reports "unusual environment" for an embedded browser; that verdict is server-side and stays out of this layer's reach.

**A Web profile may have no Browser tab.** The right-Sidebar `browser` type is disabled by default in Web profiles, and a build without the right Sidebar provides no `ctx.sidebarRight` at all; while the preference still says **In-App Sidebar**, **Chat** and **Sites** then fall back to the system browser — the same fallback `ui-chat` takes for a conversation link — and log a `console.warn` saying why. Desktop ships that tab, so it works there. In a Web build the fallback is a browser-executed `window.open` raised by a click that happened in the **pet's process** rather than a gesture in the page, so a popup blocker may refuse it; on Desktop the main process routes it through `shell.openExternal` and no blocker is involved. **Git changes** is unaffected: that page type is the plugin's own, so any build with a right Sidebar (`ui-sidebar-right` is in both profiles) can open it.

**The Git page moves local work only by explicit fast-forward pull.** Opening or refreshing the page fetches the current branch's remote-tracking ref so the status beside **Recent commits** is current, but it does not move the local branch, index, or working tree. **Pull** is the only direct action that moves local work and refuses to merge diverged history; **Commit and push** only puts a sentence in the conversation and leaves that work to the agent (above). The repository is whichever one the current Session's working directory is in, not DSH's own checkout or a configured path; a working directory outside a repository, a directory that is gone, and a machine without `git` each get their own line.

**The pet does not quit itself from the menu.** The menu's **System** submenu offers update, restart, and quit DSH — not "quit the pet": its lifetime belongs to the **Enable the pet** switch (turn it off and the pet exits; turn it on and it comes back), so stopping it has exactly one route and a stray click cannot end it. Ending DSH is that submenu's last entry, and it confirms first.

**Restarting replays a command line rather than asking the app to restart itself.** The desktop's own restart (`app.relaunch()`) lives in the Electron main process, which a plugin cannot reach: the Host is its Node-mode child and the page is sandboxed. So the pet reads its target's own command line, ends it, and starts it again the same way — which means the restart depends on that replay being faithful. Anything that existed only in the environment or the arguments of the original launch (a variable set for that one start, arguments a launcher assembled on the fly) would not be reproduced. This repository's launcher (`_mytools/build/start-desktop.bat` through `start-dsh-service.vbs`) has nothing of the sort: the environment is inherited from the parent chain and passed on unchanged. The starting directory is a heuristic too (the last token in the command line that names a directory). The robust alternative is a custom window message the Electron main process handles by calling `app.relaunch()` itself — the pet already posts `0x8001` to that window — which would mean rebuilding the desktop package and recording the patch in [UPSTREAM.md](UPSTREAM.md).

**The position only clamps to the virtual screen.** A changed monitor layout pulls the window back into view but does not remember a position per display.

**Four frames per expression.** The art fixes each state to a four-frame loop; finer motion (typing, a Zzz bubble) needs new art dropped into the matching state directory.

**The listening frames are hand-added.** `assets/music/1.png … 4.png` and the `music` key in `frames.json` were added by hand rather than sliced from a sprite sheet, so `tools/build-assets.py` — which writes `frames.json` from the sheets it slices — drops that key when the sheet-backed states are regenerated. The pet counts frames from disk, so playback still animates without it; the smoke test fails on the missing key, which is the signal to add it back.

**The menu's volume slider is configuration, so the page performs it.** The **Volume (N%)** slider writes the field the settings card writes, and the settings service refuses any write made inside an HMR transaction — which is the context the Host's timer runs in, because that timer was created while the plugin was being loaded. That command therefore reaches the page, as the other menu entries that change something already do, and it does nothing while no page is listening. **Links are the card's alone**: adding and removing them happens where a text field and a list can be shown, so the list has one owner. Everything else in **Music** — playback, the folder, and filling in missing songs — stays with the Host and works with no page open.

**The web profile is second class.** There the pet has no DSH window to control, so its right-click menu keeps only **Chat**, **Sites**, **Git changes**, **open working directory**, **mini games**, **music**, **screenshot**, **Special**, and **settings** (no **System** submenu — there is no Desktop process to rebuild or close — and no window utilities anywhere), and a click does nothing; everything else — the window, expressions, dragging — behaves the same. **Sites**, like **Chat**, prefers the right-Sidebar Browser tab, which a Web profile leaves disabled by default — the address then falls back to the system browser with a warning. **Git changes** works there too, and so does **open working directory**: it is the Host that opens the folder, with no part of the right Sidebar involved. **Screenshot** is the pet's own work and needs no window either, and **Settings** is a page rather than a window, so it behaves the same as on Desktop. **Music** behaves the same as on Desktop as well: the submenu and the audio live in the pet process, and the Host does the downloads.

**Multi-machine is a soft KVM rather than a remote desktop.** Injected input reaches neither a window running elevated ("as administrator") nor the UAC secure desktop, and mouse movement is mapped by screen proportion rather than as 1:1 displacement. Only keyboard and mouse travel — no clipboard, no files, no picture. Stutter comes from the link rather than the mapping (a wired segment measured 0–1 ms; one laptop's Wi-Fi carried 2–619 ms end to end), so the fixes are on that machine: stop the wireless adapter from saving power, prefer 5 GHz, or use a cable.

**Only the links travel between machines.** The repository's [../../settings/pet-settings.yml](../../settings/pet-settings.yml) carries the `musicLinks` array, and nothing else of the music library, so a second machine has the list and no audio until it fills it in — that is the design rather than a defect, because the audio is large, is not something this repository should carry, and can be downloaded again from its link. Playback is the pet's own work too: quitting the pet or closing the plugin stops the music, and changing `musicDir` does not migrate what was already downloaded.

<a id="dev-note"></a>
### Dev note

```text
python tools/build-assets.py          # regenerate assets/ (bundled DSH Python: Pillow + numpy)
node tests/smoke.mjs                  # state machine, art, state-file write, one real screen capture, and pet.ps1 -SelfTest (no window)
node tests/smoke.mjs --pet            # additionally runs the apply() lifecycle: start the pet, measure
                                      # that its window is on screen, change state, dispose
                                      # (a real pet window appears for about 25 seconds)
```

Re-slicing needs the source sprite sheets back: they are no longer in the repository (`git log --diff-filter=D --oneline -- _mytools/Plugins/dsh-littleIcon/IconImage` finds the deletion, and `git checkout <that commit>^ -- _mytools/Plugins/dsh-littleIcon/IconImage` restores them), or point the script at a sheet set kept elsewhere with `--source`. The default `--source` is the restored path.

`--pet` genuinely shows a pet window, in the top-left corner and in its own temporary `$DSH_HOME`, so it can run beside a pet somebody is actually using; the run prints a line saying so. The corner placement is deliberate: a strange pet in the top-left is this test, not a second pet some plugin started.

Changing `index.js`, `music.js`, `package.json`, or `cordis.patch.yml` needs a DSH restart (the host half does not hot reload — the menu's **System ▸ Restart DSH** does it now); a plugin installed into the profile as a `link:` serves `client.js` from the file itself with no separate build step, so changing it is a page refresh — and if the settings card is still the old one after that, restarting DSH once is the surest route — while `_mytools/build/sync-plugins.bat` carries `music.js` in the single-file list it refreshes for a `file:` copy; changing `pet/pet.ps1`, `pet/labels.json`, or `assets/` needs only a pet restart (switch **Enable the pet** off and on, or restart DSH).

The pet's restart only runs its whole chain (waiter → replayed command line → new instance) when it is actually chosen, so `tests/smoke.mjs` covers what it can: `pet.ps1 -SelfTest` prints the replay directory it resolves and the waiter script it would run, which the test asserts against — that `ELECTRON_RUN_AS_NODE` is dropped before anything starts, that DSH is waited out and four more seconds pass, and that cmd is the layer expanding the command line. The replay itself is meant to be checked by hand: choose **System ▸ Restart DSH** and watch the application come back.

**Open working directory** is covered down to the Host the same way: `openWorkingDirectory` is driven with an injected launcher (so no folder is really opened) and the route through a host instance that starts no pet (so no failure box appears), while the entry actually opening an Explorer window is checked by hand — together with the line it shows when the directory is gone.

**Screenshot** is covered without a person in the loop: `pet.ps1 -ShotProbe` takes one real 320×200 capture of the screen corner, and `tests/smoke.mjs` asserts that what it wrote is a PNG of exactly those dimensions with the byte count the probe reported. `pet.ps1 -SelfTest` covers the rest of what can be checked without a screen — that a capture is named and lands in `shots/` beside the state file, that a drag running up and to the left selects the same rectangle as one running down and to the right, and the **Sites submenu**: it builds that submenu once for an empty list and once for two sites, prints what each turned into (the `site-menu:` line) and fires the first entry, which the suite asserts — an empty list still says so and still offers **Manage sites**, each site carries its own address, a row with no note is named by its address, and clicking one writes *that* entry's address into the command file. It also prints which ShowWindow command brings DSH back (the `show-commands:` line), which the suite asserts — `SW_SHOW` (5) for a window this pet merely hid, `SW_RESTORE` (9) for a minimized one — and whether a click hides or raises (the `click-intent:` line), which it asserts too: only a window that is already in front is tucked away, while one that is behind or away is raised. What needs a window is checked by hand: choose **screenshot** from the menu and drag a region.

**Music** is covered the same way the screenshot is: `pet.ps1 -MusicProbe <file>` runs only the audio segment — the media player, the decoder, the sound device, and one file, with no window, no menu, and no library — and prints `music-probe: opened duration=…` on success, or `music-probe: failed error=…` and exits 1 on failure, which is the same purpose `-ShotProbe` serves: a machine that cannot play what was downloaded fails there instead of at the first menu click. `tests/smoke.mjs` drives the library, the published `music.json`, and all five routes against a host instance that starts no pet; `pet.ps1 -SelfTest` builds the music submenu for a library with tracks and asserts what every row turned into, including that the folder entry and the fill-in entry ask the Host for that work; and `tests/smoke.mjs --pet` runs the whole chain with a real pet window.
