# @local/dsh-little-icon

English | [中文](README.zh.md)

## Summary

The pet is a **process of its own** (PowerShell + WPF), not an overlay inside the DSH window: it owns a frameless, transparent, always-on-top window, so it stays on the desktop while the DSH window is minimized or tucked away. The host half (`index.js`) samples agent state into a state file; the pet switches its animation from it. Clicking the pet calls user32 `ShowWindow` to tuck the DSH window away or bring it back, and its right-click menu offers the same action plus a position reset and quit. Its first two menu entries belong to the page: **Chat** opens chat.deepseek.com in DSH's embedded browser, and **Git changes** opens a read-only repository page in the right Sidebar — the current Session's uncommitted changes on the left, its last ten commits on the right. The plugin changes no conversation, model request, or session log.

## Use this package

**Desktop install.** Desktop owns its own configuration (`$DSH_HOME/profiles/desktop`) and refuses `dsh plugin --profile desktop`; fill this directory's absolute path into the application's **Plugins → Add plugin** dialog once per machine. Desktop must then be restarted: the host half (`index.js`) takes no part in client hot reload, so only a restart loads it.

**Web install** (optional; there the pet only floats and controls no window). `build/start-dsh.bat` already lists this plugin in `DSH_LOCAL_PLUGINS`, so every start idempotently installs this directory into the web profile as a `file:` copy, and `sync-plugins.bat` refreshes `index.js`, `pet/`, and `assets/` with it. To install it by hand:

```text
dsh plugin --profile web add file:<repo>/_mytools/Plugins/dsh-littleIcon
```

**Size and translucency.** Open the **Plugins** list and click the **Desktop Pet** card: the settings card is drawn on that card's page, between the description and the parts list, so nothing hides behind the `little-icon` row. It leads with:

- **Size** — a 96–320 pixel slider; the pet takes the new size within a frame;
- **Translucent while idle** — a switch; turn it off and the pet never fades;
- **Translucency** — available while that switch is on, 15%–100%;
- **Tuck DSH away behind another app** — on by default, with its **tuck away after going behind** slider (0 seconds) greyed out while the switch is off;
- plus enable, always-on-top, click behaviour, and animation pace, with idle pacing, the happy duration, and the state sampling interval folded under **More**.

Controls write straight to the profile configuration (the `little-icon` entry in `$DSH_HOME/profiles/<profile>/cordis.patch.yml`) and need no restart: the host republishes the state file on a config change and the pet applies it within a second. Toggling **Enable the pet** off and on also ends and restarts the pet process at once. The card comes from the plugin's own browser half (`client.js`), so no second, automatically generated form appears after a restart.

**Interaction.** The pet starts in the bottom-right corner of the primary screen, as translucent as configured, and fully visible under the pointer. Dragging with the left button moves it (the position is stored on release, restored on the next start, and clamped onto the current virtual screen). A **click** — a press that did not move the window — performs the configured `clickAction`: `toggle` (default) tucks a shown DSH window away and restores plus foregrounds it on the next click, `minimize` only minimizes, `none` does nothing. Its right-click menu offers the same entries — Chat, Git changes, tuck/show DSH, move to corner, restart DSH, quit DSH. Besides your own clicks, the pet tucks DSH away on its own once DSH goes behind — see "Tucking DSH away behind another app" below.

**Right-click menu.** Right-clicking the pet opens the plugin's only menu — the pet no longer has a tray icon of its own, because DSH's main process already keeps one and an accessory should not add a second. Its first two entries belong to the page, the rest act on the window. **Chat** brings DSH back on screen and to the front first — tucked away, minimized, or merely behind another window — and only then opens <https://chat.deepseek.com> in DSH's own **right-Sidebar Browser tab**, never in the system browser, the same embedded surface DSH uses for chat links in a conversation when the link preference selects "In-App Sidebar". **Git changes** restores the window the same way and then opens the plugin's own **Git page** (below) in the right Sidebar: the current Session's working directory, with its **uncommitted changes** (including new, untracked files) on the left and its **last ten commits** on the right; double-clicking a row on either side opens what is behind it — that file's diff, or that commit's files. Restoring the window first is not optional: a tab opened in a window nobody can see is a tab nobody sees. The window entries are **tuck/show DSH**, **move to corner**, then **restart DSH** (which asks first, then ends DSH and starts it again exactly as it was — below) and last **quit DSH**, which asks for confirmation first (quitting interrupts whatever is running) and then **ends the Electron main process of DSH**. That entry used to post `WM_CLOSE` to the DSH main window — the same route as its own title-bar close button — but the desktop now makes closing a window **hide it to the tray** (the X button only tucks DSH away), so that route no longer ends anything. Ending the main process makes the Host child notice the closed channel and run its own shutdown (sessions flushed, agents stopped); that shutdown unloads the plugin, whose cleanup ends the pet with it, and a timer's host-liveness check is the fallback. The pet process draws the menu and the page performs what it chooses, with the Host carrying the choice between them; where the page has no Browser tab to open (a Web profile leaves it disabled), **Chat** only logs a warning instead of failing — **Git changes** needs no shipped tab type, so any build with a right Sidebar can open it. **The pet never quits itself from the menu**: its lifetime belongs to the **Enable the pet** switch, and a menu entry that ended it would bypass that switch.

**The Git page.** **Git changes** opens one page in the right Sidebar, split into two scrolling columns:

- **Uncommitted changes** on the left: everything `git status --porcelain` reports — staged, unstaged, and **untracked new files** (with `-uall`, so files inside a new directory are listed one by one rather than collapsed into the directory name). Each row carries the status word (new, modified, deleted, renamed, copied, conflicted, type changed), the path, and, for the entries already in the index, a "staged" marker;
- **Recent commits** on the right: the last `10` commits, each on three lines — the **message** (wrapped, so a long subject is never cut off), the **short hash**, and the author with the local time.

**Double-clicking any row** hands both columns over to whatever that row is about, always under a **Back** button that returns to the listing:

- **A row on the left** (an uncommitted file) opens **that one file's diff**: its status word and full path sit in the header, and the text below is `+` green, `-` red, `@@` blue, file headers and `index` lines grey — keeping its own line breaks and scrolling sideways instead of wrapping. A diff past 200,000 characters is sent cut short, with a line of its own saying so. A tracked file is compared on whichever side of the index holds the change — both sides when both do, one block above the other — and an untracked new file is compared against an empty one, so a file that was just added still has a diff to show; `HEAD` is never the other side of the comparison, which is why a repository with no first commit yet works too.
- **A row on the right** (a commit) opens **the files that commit touched**: its message, the file count, and the short hash sit in the header, and each file is a row below — the status word (new, modified, deleted, renamed, copied, type changed) and the path, with a rename showing where it came from as "← old path" on the same row, because a move is one thing rather than a deletion plus an addition. A merge commit is compared against its **first parent**, so what it brought in is what you see instead of an empty list, and a commit that changed nothing says so in a line.

While a detail is open, **Refresh** re-reads that detail rather than dropping you back on the listing, and changing the Session or the working directory returns to it. A row highlights under the pointer, and its tooltip says what double-clicking it does.

A header line above them shows the repository root, the current branch, a **Refresh** button, and a **Commit and push** button. The page itself only reads: it never runs Git itself — nothing stages, commits, pushes, or reverts — and double-clicking a row only has the Host read the diff or the file list behind it. The repository is whichever one the **current Session's working directory** is in, not a configured path — so the page follows the project the conversation is in, and a Session started in a subdirectory still shows the whole repository. A working directory outside every repository, a directory that is gone, and a machine with no `git` each get their own line and disable that button; an empty repository (no first commit yet) is a normal state, with both columns saying they are empty.

**The Commit and push button.** It performs no Git operation itself; it **speaks for you**: it sends "提交并推送" into the current conversation as a **real user message**, through the same Host admission the composer uses (`ctx.conversation.send`, a queued turn). The message therefore appears in the conversation, enters the session log, and reaches the model; it joins the queue when a turn is already running and starts one immediately when nothing is, and the agent then commits and pushes with its ordinary tools, writing the message by whatever convention the repository keeps. The button reports "Sent" (or "Queued" while a turn is running) where it stands, and shows the reason underneath when the message could not be sent — no live input channel for this Session, or the Host refusing the admission. **There is no confirmation step**: one click is your asking for it.

**Configuration fields.** The card's controls write these; every field applies live (a config change republishes the state file and reschedules the sampling timer, and the pet re-reads the state file, so nothing needs a restart):

| Field | Default | Meaning |
| --- | --- | --- |
| `enabled` | `true` | Turning it off ends the pet process; turning it back on starts one |
| `size` | `160` | Window edge in pixels; the frames are built at 256px and scaled down |
| `translucent` | `true` | Whether the pet fades while the pointer is away |
| `idleOpacity` | `0.45` | How far it fades; hover is always 1. Ignored while `translucent` is off |
| `frameMs` | `600` | Milliseconds each animation frame stays on screen |
| `pollMs` | `800` | Host sampling interval; lower follows the agent sooner, higher costs less |
| `happyMs` | `3000` | How long a finished task keeps it happy before it idles again |
| `boredEverySeconds` | `60` | While the agent is idle, how often a bored interruption comes around |
| `boredMs` | `5000` | How long each bored interruption lasts |
| `sleepAfterSeconds` | `600` | Seconds without activity before it sleeps, while DSH is on screen |
| `sleepWhenHiddenSeconds` | `20` | The same once DSH is tucked away, where dragging the pet is the only activity |
| `autoHide` | `true` | Never while DSH itself is in front; whether going behind another application tucks it away |
| `autoHideSeconds` | `0` | How long DSH may stay behind before that tuck; `0` tucks it at once. A running task does not postpone it |
| `topmost` | `true` | Whether the pet stays above other windows |
| `clickAction` | `toggle` | `toggle` / `minimize` / `none` |

**State to expression.** One run reads as `working` right away (no startle first) → `alert` (startled) while it waits for your decision, held for as long as the question stands → `happy` when it ends → `idle`.

- **Boredom** follows whether a task is running rather than the mouse: while the agent is idle, `bored` interrupts every `boredEverySeconds` for `boredMs`, so a long answer still shows it now and then, and any activity ends the current interruption.
- **Sleep** follows activity, on two timers. While DSH is on screen it takes `sleepAfterSeconds` without pointer, wheel, or keyboard input on the page, a drag of the pet, or a click on it — any of those wakes the pet into idle at once. Once DSH is **tucked away**, the `sleepWhenHiddenSeconds` timer applies (20 seconds by default), where the only possible activity is dragging the pet or bringing DSH back by clicking the pet.
- **It holds the startle while it waits on you.** While a question with options or an approval is unanswered, the pet switches to `alert` (startled) and **keeps it up until you answer** — that is the "it is your turn" signal, and it reads even while DSH is tucked away. The host observes the `user-questions/request` and `approval/request` waterfalls (observation only, always delegating with `next()`) and notes the agent waiting for the user: that agent is not working then, and the pet does not fall asleep inside the run, because the person is what it waits on. The answer returns it straight to `working`, with no second startle. Input queued behind that question is not work either, since the person answers first.
- **Tucking DSH away behind another app** (`autoHide`, on by default) reads who is in front rather than whether anything happened: DSH itself in front is never tucked away, so a long answer no longer disappears while you read it. Once another application comes to the front — your editor, your browser — the pet tucks DSH away, and `autoHideSeconds` (0 by default) is the grace period after that switch, with 0 meaning the next sample. **Whether a task is running makes no difference** — the task keeps going, the window goes first. This only ever applies while DSH is still on screen; a minimized or already tucked window is left alone. DSH's own dialogs and update prompts, and the pet's own window, all count as DSH's side, so dragging the pet never tucks DSH. Clicking the pet (or DSH's own tray icon) brings DSH back and makes it the front window in the same step, so it is not tucked again immediately.

The pet writes whether DSH is on screen and whether it is DSH's side that is in front (its main window, one of its dialogs, or the pet itself) into `window.json`: the first selects the sleep timer, the second decides the auto-tuck, and a change in either counts as activity by itself. Each state is a four-frame loop.

Local data lives under `$DSH_HOME/little-icon/`: `state.json` (written by the host, read by the pet), `position.json` (written by the pet), `window.json` (the pet's report of whether DSH is on screen and whether it is in front), `command.json` (the pet's right-click menu choice, which the host reads and relays to the page), and `quit` (the host's "please exit", which the pet answers by storing its position and closing its own window in order, taking the request with it). It is per machine and never syncs with the repository; deleting it restores the default position and state.

## Understand the implementation

<details>
<summary>Implementation details — click to expand</summary>

**Why a separate process is required.** The desktop shell exposes no window capability to plugins: the main window's `BrowserWindow` sets neither `transparent` nor `alwaysOnTop` nor `skipTaskbar`, `apps/desktop/src/ipc.ts` lists no minimize/hide/restore channel, and `preload-app.ts` exposes only `dshDesktop` (browser views and updates), `dshPlatform` (the usage/top-up embedded page), the directory picker, host paths, and the locale. The shell does own a tray icon of its own (`apps/desktop/src/tray.ts`), but a plugin cannot add entries to it or draw in it. The renderer runs with `sandbox: true` and `contextIsolation: true`, and `window.open` is denied outright. Decisively, plugin host code runs in the `ELECTRON_RUN_AS_NODE=1` Node child process (`apps/desktop/src/host-process.ts` plus `node-environment.ts`), where `require('electron')` yields the binary path and nothing more. A hidden window stops painting its DOM as well. "The pet stays after DSH is tucked away" therefore needs a process the plugin starts itself.

**Browser half.** `client.js` does four things. It registers a hand-written settings card into `plugins.bundle.config`, the seat the Plugins page keeps for one bundle's own configuration, keyed by the package name `@local/dsh-little-icon` — drawn right on the plugin list's card page, one click shallower than the `little-icon` row's own page. The card reads no configuration itself: `ctx.configForms.get('little-icon')` yields the row's form, whose accepted sections are mirrored into a snapshot store and handed to the component through the registration's inject face (`hooks.petSettings` plus a `write` callback), so the Host schema stays the single owner of every value. Sliders echo locally while dragging and collapse into one write 250ms after the drag settles; switches and the select write at once. The host half therefore calls `settings.configure({ auto: false })`, so the same fields never appear twice in a generated English form. Second, it reports user activity (next paragraph). Third, it performs the pet's right-click menu commands: it subscribes with `new EventSource('/api/little-icon/commands')` and, on `chat`, calls `ctx.sidebarRight.openTab('browser', { params: { url: 'https://chat.deepseek.com' } })` — the right-Sidebar Browser tab is the only way a plugin opens a site inside DSH, and it is what `ui-chat` uses for conversation links. `sidebarRight` and `sidebarRightTabs` are looked up through `ctx.get` rather than injected (a Web profile may leave the `browser` type disabled, and a build without the right Sidebar provides no service at all); when either is missing the command only logs a `console.warn`, because this card has to load in every profile. All copy lives in `ctx.locale` dictionaries (Chinese and English); `tests/smoke.mjs` asserts the two cover the same keys, that the card asks for nothing else, drives one immediate write and one merged drag through the real form API, checks that the activity listeners register and throttle, drives a `chat` command plus both unavailable-service paths and the `EventSource.close()` that disposal performs, and renders the Git page from a seeded repository answer. It also renders the state a double-click leads to, asserting that the detail replaces both columns, that the Back button is what returns, that every diff line carries its own tone, that a commit's rows carry the listing's status words with a rename showing its source, and that an empty, truncated, or failed read each says so in the detail's own place. Fourth, it provides the **Git page**: the `git` command calls `openTab('little-icon-git')`, and that page type is one this plugin registers itself, through the right Sidebar's own two stages — `ctx.sidebarRightTabs.register({ id, kind, title })` says what the type is, and a component registered under the same `id` in the keyed `sidebar.right.pane.tab` seat draws its body. The registry admits types from outside the product by design, so the page needs neither the Browser tab nor any shipped viewer; the whole registration hangs off `ctx.inject(['sidebarRightTabs', 'slots'], …)`, which never runs in a build without a right Sidebar while the settings card above still loads there. The component reads no file: its inject face supplies three reads — `load(cwd, signal)` over the Host's Git route, `loadDiff(root, path, signal)` for one file's diff, and `loadCommit(root, hash, signal)` for one commit's files, the last two carrying the repository root rather than the Session's directory because the path the listing gave is relative to that root (the Host is what looks a path's status up, and what asks for a commit's parents, before deciding which comparison to run) — while `useSessions` supplies the current Session's working directory and `useTabInfo` supplies this navigation's `revision`, so choosing the menu entry a second time re-navigates the same tab and refetches, which is the same path the Refresh button takes. Opening a row's detail is a state in that component: a set `detail` replaces both columns, draws a diff or a file list from its `kind`, gives each kind its own header, and the Back button sets it back to `undefined`, so the listing is never fetched again just to come back. The same face's `sendPrompt(text)` is what the **Commit and push** button calls, and it borrows the Session's own scope to reach `ctx.conversation.send` — the composer's admission, not a private channel: a Session nobody holds resolves no scope and answers `no-channel` instead.

**Where "activity" comes from.** The Host sees agents and jobs, and "nobody has touched anything" is not the same as "no task is running" — without an input signal the pet would sleep while the person keeps using DSH. The browser half therefore pings `POST /api/little-icon/activity` on `pointerdown`, `pointermove`, `wheel`, and `keydown`, throttled to one every 15 seconds. That route is same-origin, checks `connection.requestRejection` first like the repository's own routes, and answers 405 to anything but POST. The Host takes the newest of that timestamp and the pet's `position.json` modification time, so dragging the pet or using the menu's "move to corner" counts too. A tucked DSH window produces no page input at all — which is the point — so there the pet reports the window state it alone can see into `window.json` once a second (on screen, and whether DSH's side — its own windows or the pet — is what is in front), and the Host switches timers on it and decides the auto-tuck from it. Showing, hiding, or moving to and from the front counts as activity on its own, which also starts the tucked sleep timer the moment the auto-tuck lands. Sleep therefore arrives only after a stretch in which nothing at all happened, and starting a task counts as activity as well.

**Host half.** `index.js` samples every `pollMs`: `ctx.get('agents')` for an agent that is `running` or holds queued next-turn/next-step work, and `ctx.get('jobs')` for a `running` or `stopping` job (the same test `apps/desktop-host/src/update-tasks.ts` uses), minus the agents blocked on a human answer: the host prepends an observer to the `user-questions/request` and `approval/request` waterfalls (delegating with `next()` itself and returning the chain's own promise) and leaves the asking agent out of the busy set while reporting it as `waiting`, which is what the state machine turns into a held `alert`; it returns to normal when the answer settles, so "the model is waiting for you to choose" is neither read as work nor missed. The decision itself is the pure `sampleState`, which `tests/smoke.mjs` drives directly; it takes "is anything running", "when did anything last happen", and the sleep timer currently in force, which the reported window visibility selects. A second pure function, `shouldTuck`, decides whether DSH should be tucked away: it sees only the window facts the pet reports — on screen, whether somebody else is in front, and when DSH went behind — plus `autoHide`/`autoHideSeconds`. DSH itself in front returns false outright, so a window you are looking at is never taken away, and "is a task running" is deliberately not an input, so a task keeps going while the window goes. Its answer is published as `tuck` in `$DSH_HOME/little-icon/state.json`, which is a command rather than a state: the visibility the pet reports back turns it off on the next sample, and a repeat of the same request in between is harmless because the pet's own window setter is idempotent. The file is written on change, plus a four-second heartbeat the pet uses to tell whether the host is still alive. Writing means a temporary file replaced by a rename, and Windows refuses that rename while any process has the file open — which the pet's own 200 ms read of state.json does — so the writer retries; a snapshot that still cannot be placed leaves the previous one in place, reports the error (at most once per 30 seconds while writes keep failing), and waits for the next sample. Nothing escapes: the harness exits the whole host process on an uncaught exception (the 2026-09-27 crash was this rename reporting EPERM), so the sampling tick and the publish a settings change triggers both run behind the same guard. `translucent` and `idleOpacity` collapse into one `opacity` field here, so the pet needs no notion of the switch. The pet is started with `child_process.spawn` (`powershell.exe -NoProfile -NonInteractive -STA -ExecutionPolicy Bypass -File pet/pet.ps1`) carrying the asset directory, the state and position files, and the process id of the window to control; the `ctx.effect` disposer ends it (asking it to quit through the `quit` file first, so it stores its position and closes its window in order, and killing it only if it does not answer within a second), so DSH leaves no orphan window. In the desktop shell the host's parent is the Electron main process, so that id is simply `process.ppid`; the web profile has no window to control and passes 0. Menu commands take another route: the pet writes its choice to `command.json`, the host reads that file once per tick (only a strictly newer `at` counts as a new command, so a record left by a previous run is never replayed) and pushes it to the page over the `GET /api/little-icon/commands` SSE stream. That stream passes the same `connection.requestRejection` check as the activity route, answers with nothing but the event stream (`text/event-stream`, opening with a comment frame so a subscriber is live at once), and is dropped from the subscriber set and `end()`ed when the client disconnects or the plugin is disposed. A command chosen while no page is listening is dropped: the page is what performs it, so with no page there is nothing to perform it.

**Git route.** The Git page's facts live on disk and the page has neither a filesystem nor a process, so the Host asks Git for them: `GET /api/little-icon/git?cwd=<Session working directory>` answers one JSON object. It confirms the directory exists first (`statSync`), because `execFile` cannot tell the two cases apart — a missing directory and a missing `git` both fail to spawn with `ENOENT`, and the page says different things about them — and then resolves the repository root with `git rev-parse --show-toplevel`. The directory finds the repository rather than the other way round, so a Session started in a subdirectory still reports the whole repository. Three read-only commands follow, concurrently: `branch --show-current` (empty on a detached HEAD, where the page then shows no branch), `status --porcelain=v1 -z --untracked-files=all`, and a `log` for the last ten commits whose fields are separated by `0x1f`. Both outputs are parsed as `-z` records, so NUL separates them and no punctuation in a commit subject can collide with a separator; a rename or copy carries its source path in the record that follows, which is why that walk advances by hand. A repository whose first commit has not been made yet makes `git log` fail, which is a normal state answered with an empty list rather than an error. The route accepts GET only and always answers 200 JSON: a missing directory, a directory outside every repository, a missing `git`, and a failed command are the four reasons `no-dir`, `not-a-repo`, `no-git`, and `failed`, which the page turns into words — machine-readable reasons rather than localized copy, because only the page knows which language to use.

**Git diff route.** Double-clicking a row asks the Host once more: `GET /api/little-icon/git/diff?root=<repository root>&path=<the row's path>`, GET only and always 200 JSON like the listing, through the same guard and the same JSON writer. It confirms the directory and resolves the repository the same way, so "the directory is gone", "not a repository", and "no `git`" get the listing's own answers here too. It then looks the path's status up itself (`status --porcelain=v1 -z --untracked-files=all --`, with the path wrapped in `:(literal)` so a `*` in a filename is not read as a glob) and runs only the comparisons that have something to say: `diff --cached` when the index side holds a change, `diff` when the worktree side does, both blocks one after the other when both do. An untracked file is compared against `NUL` on Windows and `/dev/null` elsewhere through `diff --no-index`, whose exit code 1 means "they differ" rather than failure — the diff is on stdout either way. `HEAD` is never the other side of a comparison: it does not resolve in a repository with no first commit, and `--cached` already compares the index against the empty tree there. Every call carries `--no-color --no-ext-diff`, so a configured color or an external diff driver cannot put escape codes or another program's output in the page. Text past 200,000 characters is cut and the answer says `truncated: true`, which the page states on the diff's own first line. When the path was committed or reverted between the two commands, the status query reports nothing and the answer is an empty diff (`{ok:true,text:''}`) — the page says there is no diff to show, which is a normal state rather than an error.

**Git commit route.** Double-clicking a row in the history column asks `GET /api/little-icon/git/commit?root=<repository root>&hash=<that row's full hash>`, GET only and always 200 JSON like the others, with the same directory and repository checks up front so all three "cannot read it" answers read the same way. A commit has no working tree to compare against, so its paths come from `diff-tree`, and its parents are asked for first with `rev-list --parents -n 1 <hash>`: **the first commit has none**, so the empty tree is the other side through `--root` (`diff-tree` lists no file at all for it otherwise), and **a merge has more than one**, so the first parent is what it is compared with (`diff-tree` given only the merge itself lists nothing either) — which is why a merge shows what it brought in. A hash Git does not have makes `rev-list` fail, and Git's own words travel back as `failed`. The output is parsed as `-z` records: the status first, then the path, with `R100`/`C075` the only statuses carrying two paths, source before destination — the page shows the destination as the path and the source beside it as "← old path". An empty commit answers with an empty list, which the page states in a line.

**Pet process.** `pet/pet.ps1` is a WPF frameless transparent topmost window (`WindowStyle=None`, `AllowsTransparency`, `Topmost`, `ShowActivated=false` so it never steals focus). The script declares the process DPI aware first (`SetProcessDpiAwarenessContext`, falling back a step at a time): PowerShell has no DPI manifest, and a layered window in an unaware process is rendered into a surface at the virtualized size and then stretched by the system, which tiled the pet two-by-two and drew it larger than asked. After `WindowInteropHelper.EnsureHandle()` it adds `WS_EX_TOOLWINDOW` to the handle, because WPF's `ShowInTaskbar=false` does not actually set that style and the pet would otherwise appear in the taskbar and Alt+Tab. A 200ms timer re-reads the state file when its write time moves, applying expression, size, opacity, click action, and topmost; frames advance every `frameMs`, and the script counts the frames on disk instead of reading a constant (most states have four, `working` has six). Dragging uses `DragMove()`. The press that activates the pet window is reported twice — once while WPF handles the activation, once as the ordinary mouse message — and that first report cannot start a drag, so a press only latches and the release decides click or drag; acting on the first report would run the click action twice and tuck DSH on a press that only dragged the pet. The position is stored in `position.json`, restored at start, and clamped onto a screen. The right-click menu (`New-PetMenu`) is the plugin's only menu, a WinForms `ContextMenuStrip`: on Desktop the first two entries are **Chat** and **Git changes**, which each call `Show-DshWindow` to restore and raise DSH (`SW_RESTORE` when it was tucked away or minimized, `SetForegroundWindow` when it was merely behind) and then write `{"command":"chat","at":…}` or `{"command":"git","at":…}` to `command.json` for the host to relay, while the remaining entries act on this process; the web profile has no system window to control, so its menu carries no tuck/show entry. The foreground fact it reports every second means "DSH's side is in front": windows of DSH's own process (dialogs, the update prompt) and the pet's own window all count, and only a third-party application in front counts as being behind — so dragging the pet is never read as your having moved to another application. Every label is read from `pet/labels.json` as UTF-8, with English defaults inside the script, which itself stays pure ASCII.

**Restarting DSH.** The entry above **quit DSH** is **restart DSH** (it asks first too, since a restart interrupts whatever is running), and what it does is "end DSH, then start it again the way it was". That cannot happen inside the pet: ending DSH unloads the plugin, whose cleanup ends the pet with it, so a **detached waiter** (a hidden `powershell.exe -EncodedCommand`) is armed first — it waits for the DSH process to really exit, waits four more seconds for the Host's shutdown (sessions flushed, agents stopped), and then acts. What the waiter replays is "how DSH was started", which only that process knows, so it reads its command line from WMI (`Win32_Process.CommandLine`) and hands it to `cmd /c` verbatim; the line never passes through a command line of our own but travels in the `DSH_RELAUNCH_CMD` environment variable for cmd to expand, so spaces, quotes and non-ASCII paths are not re-parsed by any layer in between. The working directory is **the last quoted token that names a directory**, which is what the launcher uses as its work directory (`start-dsh-service.vbs` sets `CurrentDirectory` to the application directory). One environment trap is worth naming: the pet runs under the Host, which runs under Electron in Node mode, so the whole tree carries `ELECTRON_RUN_AS_NODE=1`, and an Electron started with it runs as a plain Node process and dies on the app's first import — the waiter drops it before starting anything (only there; the pet itself still needs the environment it was given). When the command line cannot be read (no WMI), **DSH is left alone** and a message says so: doing nothing is better than ending it with no way back. Any failure while preparing the restart reports itself in a box too, saying DSH was not touched — including the one that was found the hard way: in Windows PowerShell a computed name cannot be assigned through `$env[$name]` ("Cannot index into a null array"), and because that happens *before* DSH is ended, it looked exactly like a menu entry that does nothing. That variable is now set through .NET, and a failure there speaks instead of staying in the log.

**Geometry units.** Position and clamping use WPF's own `SystemParameters.WorkArea` and `VirtualScreen*`, which share the device-independent units of `Window.Left/Top`. WinForms reports the work area and virtual screen in physical pixels, and mixing the two pushes the pet off-screen at any display scaling other than 100% — a bottom-right position lands 1.5x too far right and down at 150%. `tests/smoke.mjs --pet` measures the window from a DPI-aware probe and asserts it is inside the screen.

**Window control.** The target starts as `Process.MainWindowHandle` — the real main window, which the untitled helper windows cannot confuse, so it is trusted first. When that reports 0 (a hidden window), the pet enumerates the process's top-level windows and skips IME helpers such as `IME`, `CandidateWindow`, and `MSCTFIME UI`. The handle is cached, because `MainWindowHandle` becomes 0 after `SW_HIDE`. Tucking uses `SW_HIDE` (gone from both the screen and the taskbar, leaving the pet and DSH's own tray icon as the way back); restoring uses `SW_RESTORE` plus `SetForegroundWindow`. Every change goes through one `Set-DshWindowShown`: a click, a menu entry, and the host's `tuck` request all use it, and it returns when the window is already where it was asked to be, so a repeated `tuck` never brings a just-tucked window back; `clickAction`'s `minimize` still uses `SW_MINIMIZE` on its own.

**Encoding.** `pet.ps1` stays pure ASCII: without a BOM, Windows PowerShell 5.1 decodes a `.ps1` as ANSI, which turns UTF-8 Chinese into mojibake and can even swallow quotes into a syntax error. The localized menu labels live in `pet/labels.json`, read as UTF-8, with English defaults when it is missing. `tests/smoke.mjs` asserts the script contains no non-ASCII character.

**Art.** `assets/<state>/1.png … N.png` come from `tools/build-assets.py`, which slices one sprite sheet per expression; the finished frames are the only copy of the art in the repository (the ~24 MB of source sheets were deleted — restore them from git history as the dev note below describes). Each source sheet packs several figures onto one 2048×2048 canvas, and the layouts differ: most states are two-by-two (four figures), `working` is three columns by two rows (six), and `sleep` leaves only 14 transparent pixels between its rows. The script therefore assumes no grid and finds figures by alpha projection: empty rows split the sheet into bands (a gap under 8 pixels does not split, and bands too short to be a figure are absorbed into their neighbour so Zzz bubbles and gear icons stay attached), column valleys below 12% of the band's peak split each band into figures, and each region is then cropped to its actual opaque pixels. Figures run top-to-bottom, left-to-right, are pasted bottom-centered onto one shared canvas per state, and share a single global scale taken from the largest figure in the set, so a state never jumps between frames and the character keeps its size across expressions. The artwork decides the frame count, recorded in `assets/frames.json`; the pet counts files rather than reading a constant, so new art needs no code change.

</details>

## Model experience

None. The plugin adds no model-visible input, prompt, tool, or session event; it only reads agent and job status.

## <a id="known-limitations-and-deferred-work"></a>Known limitations and deferred work

**Errors have no expression of their own.** `agent/error` is still in the event table, while `alert` now belongs to waiting for your decision (above). Giving failures a face again is a matter of listening for that event in the host half, feeding the state machine one more input, and having the art for it.

**Activity comes only from the DSH page and the pet itself.** The report is built from input events on the DSH page, so a tucked, minimized, or covered DSH window produces none: while tucked the pet sleeps on `sleepWhenHiddenSeconds`, which is the point. Working in another application does not keep it awake; typing or clicking back in DSH, dragging the pet, or using the menu's move-home entry does.

**"Tuck away" uses `SW_HIDE`, not minimize.** The DSH window leaves the screen and the taskbar; the way back is the pet itself and the tray icon DSH's own main process keeps (`apps/desktop/src/tray.ts`: click to open the window, right-click for Open application / Quit application). The pet builds **no** `NotifyIcon` of its own: the notification area already holds one icon that belongs to DSH, and a widget hanging off DSH should not add a second. If DSH exits some other way, the pet quits on its own within 45 seconds or as soon as the host process is gone.

**Quitting the pet asks first and kills only as a fallback.** The host does not kill it outright: it writes the `quit` file, which the pet reads within one 200 ms tick (storing its position, closing its window in order, and taking the request with it), and only a pet that does not answer is killed, one second later. That keeps a normal teardown from racing the position file the pet is still writing. `tests/smoke.mjs --pet` covers both halves of that handshake: starting a pet must clear a `quit` left by a host that died mid-teardown (or the new pet would quit on its first tick), and switching **Enable the pet** off writes the request, which the pet answers by exiting and taking the request with it.

**The in-app browser does not sign in by itself.** **Chat** opens DSH's right-Sidebar Browser tab, whose storage partition is persistent (the one upstream file this working copy changes: `apps/desktop/src/browser-guests.ts` names it `persist:dsh-sidebar-browser-<digest of the workspace identity>`; the edit, the rebuild, and the restore steps are in [UPSTREAM.md](UPSTREAM.md)), so signing into chat.deepseek.com there once keeps you signed in across DSH restarts. It is not, however, signed in with the DSH account: the credentials DSH holds belong to `platform.deepseek.com` (`platform-view.ts` injects them for that origin only, which is what makes the official usage page work), while chat.deepseek.com runs its own Web session — and a plugin cannot put cookies into that partition either, because the host half has no Electron API, the browser half is sandboxed, and the partition belongs to `apps/desktop`. DeepSeek also reports "unusual environment" for an embedded browser; that verdict is server-side and stays out of this layer's reach.

**A Web profile may have no Browser tab.** The right-Sidebar `browser` type is disabled by default in Web profiles, and a build without the right Sidebar provides no `ctx.sidebarRight` at all; **Chat** then does nothing (the page only logs a `console.warn`). Desktop ships that tab, so it works there. **Git changes** is unaffected: that page type is the plugin's own, so any build with a right Sidebar (`ui-sidebar-right` is in both profiles) can open it.

**The Git page reads, and reads only the working directory.** The page runs no Git write of its own, and double-clicking a row only has the Host read one file's diff or one commit's files; its one action is the **Commit and push** button, which puts a sentence in the conversation and leaves the work to the agent (above). The repository is whichever one the current Session's working directory is in, not DSH's own checkout or a configured path; a working directory outside a repository, a directory that is gone, and a machine without `git` each get their own line.

**The pet does not quit itself from the menu.** The menu offers tuck/show DSH, move to corner, restart DSH, and quit DSH — not "quit the pet": its lifetime belongs to the **Enable the pet** switch (turn it off and the pet exits; turn it on and it comes back), so stopping it has exactly one route and a stray click cannot end it. Ending DSH is the last entry, and it confirms first.

**Restarting replays a command line rather than asking the app to restart itself.** The desktop's own restart (`app.relaunch()`) lives in the Electron main process, which a plugin cannot reach: the Host is its Node-mode child and the page is sandboxed. So the pet reads its target's own command line, ends it, and starts it again the same way — which means the restart depends on that replay being faithful. Anything that existed only in the environment or the arguments of the original launch (a variable set for that one start, arguments a launcher assembled on the fly) would not be reproduced. This repository's launcher (`_mytools/build/start-desktop.bat` through `start-dsh-service.vbs`) has nothing of the sort: the environment is inherited from the parent chain and passed on unchanged. The starting directory is a heuristic too (the last token in the command line that names a directory). The robust alternative is a custom window message the Electron main process handles by calling `app.relaunch()` itself — the pet already posts `0x8001` to that window — which would mean rebuilding the desktop package and recording the patch in [UPSTREAM.md](UPSTREAM.md).

**The position only clamps to the virtual screen.** A changed monitor layout pulls the window back into view but does not remember a position per display.

**Four frames per expression.** The art fixes each state to a four-frame loop; finer motion (typing, a Zzz bubble) needs new art dropped into the matching state directory.

**The web profile is second class.** There the pet has no DSH window to control, so its right-click menu keeps only **Chat**, **Git changes**, and **move to corner** (no tuck/show, and no restart or quit DSH — there is no window to close), and a click does nothing; everything else — the window, expressions, dragging — behaves the same. **Git changes** works there too.

### Dev note

```text
python tools/build-assets.py          # regenerate assets/ (bundled DSH Python: Pillow + numpy)
node tests/smoke.mjs                  # state machine, art, state-file write, and pet.ps1 -SelfTest (no window)
node tests/smoke.mjs --pet            # additionally runs the apply() lifecycle: start the pet, measure
                                      # that its window is on screen, change state, dispose
                                      # (a real pet window appears for about 25 seconds)
```

Re-slicing needs the source sprite sheets back: they are no longer in the repository (`git log --diff-filter=D --oneline -- _mytools/Plugins/dsh-littleIcon/IconImage` finds the deletion, and `git checkout <that commit>^ -- _mytools/Plugins/dsh-littleIcon/IconImage` restores them), or point the script at a sheet set kept elsewhere with `--source`. The default `--source` is the restored path.

`--pet` genuinely shows a pet window, in the top-left corner and in its own temporary `$DSH_HOME`, so it can run beside a pet somebody is actually using; the run prints a line saying so. The corner placement is deliberate: a strange pet in the top-left is this test, not a second pet some plugin started.

Changing `index.js` or `package.json` needs a DSH restart (the host half does not hot reload — the menu's **Restart DSH** does it now); changing `pet/pet.ps1`, `pet/labels.json`, or `assets/` needs only a pet restart (switch **Enable the pet** off and on, or restart DSH).

The pet's restart only runs its whole chain (waiter → replayed command line → new instance) when it is actually chosen, so `tests/smoke.mjs` covers what it can: `pet.ps1 -SelfTest` prints the replay directory it resolves and the waiter script it would run, which the test asserts against — that `ELECTRON_RUN_AS_NODE` is dropped before anything starts, that DSH is waited out and four more seconds pass, and that cmd is the layer expanding the command line. The replay itself is meant to be checked by hand: choose **Restart DSH** and watch the application come back.
